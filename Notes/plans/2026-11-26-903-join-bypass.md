# #903: `join(playerID:)` bypasses CanJoin and the player limit

**Status:** rev 1, plan only (2026-11-26). The code lands after K1b-5's move commit and before K2-1.

## Problem

`LandKeeper.join(playerID:clientID:sessionID:services:)` is public. It runs a join flow of its own:
- it runs no CanJoin;
- it makes no player-limit check (`MaxPlayers`);
- it takes no rejoin reservation;
- it does no stale-join check (#234).

It keeps the duplicate-login kick, the drain guard and OnJoin. Its doc says it "creates a PlayerSession internally and calls the new join method", which it doesn't.

The transport never reaches it: the transport joins through `LandKeeperProtocol.join(session:…)`, via `joinReportingAdmission`. So the bypass is open only to an embedder that calls the keeper directly, and to tests.

Consulted:
- `Notes/plans/2026-11-25-852-duplicate-login-cap-options.md` §2 lists this overload as "a separate, older gap". It caps the overload only if the maintainer wants it capped at all.
- `Notes/plans/2026-11-25-k6-join-and-reconnection-survey.md` notes the same: "no cap check at all".

A wrapper that forwards to `join(session:)` gets K6's change with nothing of its own to move. A second flow, the legacy G segments, would need K6's change done twice.

## The fix: the overload forwards to `join(session:)`

```swift
/// Joins `playerID` through the land's admission (CanJoin, `MaxPlayers`), as
/// `join(session:clientID:sessionID:services:)` with a `PlayerSession` of that player ID. A denial
/// throws `JoinError.custom` with CanJoin's reason.
public func join(playerID: PlayerID, clientID: ClientID, sessionID: SessionID, services: LandServices = LandServices()) async throws {
    let decision = try await join(session: PlayerSession(playerID: playerID.rawValue), clientID: clientID, sessionID: sessionID, services: services)
    if case .deny(let reason) = decision { throw JoinError.custom(reason ?? "join denied") }
}
```

The flow it ran is deleted:
- `LegacyJoinRequest`, `LegacyJoinCall`, `legacyJoinBegin`, `legacyJoinInsert` and `legacyJoinAppend`, the G segments #896 added (K1b-5 plan §4.2);
- K1b-5 plan §4.2's table, kept as a note that points here.

The `KeeperModel.swift:29` comment loses its legacy clause.

Why this one:
- **It makes the doc true and closes the bypass, with no call site touched.** The signature stays, and the statement form `try await keeper.join(playerID:…)` stays valid.
- **One join flow.** K2-1's machine, K2's entry matrix and K6 each meet one join flow, not two. With the G segments gone, the move's follow-ups have less to carry.
- **No new API.** The denial reuses `JoinError.custom`. A dedicated `.denied(reason:)` case would be a public enum change; Q1 asks.

Rejected:
- **`package` and renamed `…ForTesting`.** This touches 275 call sites, keeps the second flow alive into K2, and leaves the doc problem in place under a new name.
- **Delete the overload, and rewrite every caller to `join(session:)`.** The same 275 sites, each also needing `_ =` for the returned decision. It buys nothing over forwarding.

### What changes for a caller

- A land with CanJoin now runs it. A denial throws `JoinError.custom(reason)`; before, the player joined anyway.
- `MaxPlayers` is now checked: a join past the cap throws `JoinError.roomIsFull`.
- The join takes a rejoin reservation across its awaits, like the transport's join.
- The player's entry gets the `PlayerSession`'s fields: `deviceID` nil, `isGuest` false, `metadata` empty. P-903-1 shows no test or record pin sees a difference.
- On a re-evaluation keeper, both paths skip OnJoin for a viewer (the same guard).

## Where and when

- **After K1b-5's move commit.** The G segments are among what the move rewrites; deleting them before it would conflict with the move in progress.
- **Before K2-1.** K2-1 should model one join flow.
- In its own small PR on main, not inside the move.
- It doesn't collide with K6: K6 changes `joinReportingAdmission`'s inside, which the wrapper calls.
