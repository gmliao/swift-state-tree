# Development speed: CI wall-clock and local builds (measurement and plan)

**Status:** measurement and plan only. No workflow or code changes are in this commit.

**Question:** where do the minutes between a push and a complete CI result go, and which changes save the most of them for the least risk?

- **Queueing isn't a cost.** The repository is public. Over 255 jobs of 40 recent runs, the wait from a job's creation to its start was 0.0 min at the median, 0.8 min at p90 and 6.0 min at most. A push's wall clock is therefore its slowest job: **e2e-game, about 18 minutes**.
- **Volume.** From 2026-11-11 to 2026-11-18 there were 259 runs of each workflow (one per push), and 18 reruns (attempt > 1): 14 of Swift Build & Test, 4 of E2E Tests.
- **Runner time per push:** about 98 job-minutes, the sum of the medians.

One e2e-game log (run 44320129353, in-turn sync true), by its section lines:

- **The three encodings, one after another: 5.5 min.** json 1.3, jsonOpcode 1.4, messagepack 2.5. Messagepack also runs the record and verify scenarios, each with an offline `ReevaluationRunner` (about 0.1 min each, already built).
- **The row-addressing-off step: 6.8 min.** It is the same three encodings again, against a build that is now warm (`Build complete! (12.02s)`). The tables-off variant inside it is skipped on the row-addressing-on step.

So e2e-game is one build plus the scenario suite twice, in series.

### Build variants: one binary

The four Swift build jobs differ only in environment variables:

| Job | Variables |
|---|---|
| build (in-turn sync true / false) | `IN_TURN_SYNC` |
| build (sync tables off) | `USE_SYNC_TABLES=false`, `TYPED_LEAF_VALUES=false` |
| build (per-player sync tables off) | `PER_PLAYER_SYNC_TABLES=false` |

Each is read at run time through `EnvKeys` / `TransportEnvKeys`. `Package.swift` defines no compile-time flags, and the only conditional compilation in `Sources/` is `#if DEBUG`. So every variant runs the same debug binary, and each job builds it again from nothing: cold, with dependency resolution, about 4 to 5 minutes of each job. Seven jobs build Swift code from a clean checkout this way, plus the two e2e-game legs. No job caches `.build` or the package checkouts. `actions/cache` is used for npm only.

### The clean step in build-and-test.yml

`rm -rf .build` and `swift package clean` came in with 94bada97 (2026-01-17, "Clean build artifacts … to avoid invalidPayloadSize errors"). The same commit removed `-v` from `swift build` and `swift test`, and its message ties the error to verbose output rather than to a stale `.build`. On a fresh runner with a fresh checkout there is no `.build` to clean, so the step does nothing and costs nothing today. It matters only once a cache restores `.build`: then it would throw the cache away.

### Flaky tests that cost reruns

- **#466 (open):** `LoadTestPacingTests` in `Examples/GameDemo` bounds wall-clock times: a 40 ms start lag, a 900 ms total, a 30 ms and a 20 ms wake. On a loaded runner they fail. Two of them failed attempts 1 and 2 of the `examples` job on run 44329267068, a change that didn't touch load-test code. Each rerun of `examples` costs about 13 minutes and a person's attention.
- **The same class, closed:** #438 and #447. `ResolverTestLandTests` checks a lower bound (`>= 50 ms`), which load can't break.
- These tests measure a clock, so `HoldPoints` / `TestGate` don't fit. They need the pacing code to take a clock that the test advances.

### The local Mac

Apple Swift 6.4.2, arm64. Local verification runs one build at a time.

| Build | Time |
|---|---|
| Cold debug build with tests (a fresh worktree, `swift test`) | 313.89 s |
| Release build with tests in a worktree whose release build had been stopped at about 1604 of 1673 steps the day before (so not fully cold) | 410.41 s |
| Incremental debug build after the release run, same worktree | 20.70 s |
| Incremental `swift build --build-tests` after edits in `Sources/` (three runs) | 113.88 s, 131.02 s, 148.36 s |
| `Examples/GameDemo` `swift build -c release` (the library in release) | 309.63 s |

On the Mac the build dominates, not the tests. Two observed waits for the local build on 2026-11-18 were 47 and 50 minutes, each while another change ran its full verification. That's two observations, not a distribution: the waits aren't logged.

## Levers, ranked

Minutes are the push's wall clock unless marked as runner minutes. Today's critical path is e2e-game (17.9). After it come examples (13.0) and build (10.8).

| # | Change | Saves per push | Risk | Notes |
|---|---|---|---|---|
| 1 | **Split e2e-game's row-addressing-off step into its own matrix legs** (in-turn sync × row addressing: 4 legs instead of 2) | **about 5 min**: e2e-game drops to about 11, and examples (13.0) becomes the critical path | Low: same steps and checks, and each step already writes its own `E2E_TMP_DIR` | Costs about 2 × 5 runner minutes for the extra builds |
| 2 | **Move the deep-research Python tests out of `examples`** into a job without the Swift container | **about 2 min with lever 1** (examples drops to about 8; e2e-game at about 11 is critical again); 0 alone | Very low: the 15 test files call neither Swift nor a subprocess | The 4.7 min likely includes installing python3 in the Swift image |
| 3 | **Cache SwiftPM's dependency checkouts** (`.build/repositories`, `.build/checkouts`), keyed by `Package.resolved` and the toolchain image | about 1 min on every Swift job, on the critical path too | Low: SwiftPM checks out the pinned revisions; a miss costs what today does | The clean step must not delete them: drop it or narrow it |
| 4 | **Fix #466 with an injected clock** in `LoadTestPacing` | about 1 min on average (18 reruns over 259 pushes, about 7 %; an `examples` rerun costs about 13 min), and the reruns' attention | Low: test and Examples code only | Same pattern for any other wall-clock bound found |
| 5 | **Cache `.build` of our own code**, keyed by the toolchain, `Package.resolved` and the sources | up to 3–4 min a job on a hit; unknown on a PR push, where the sources changed | Medium: a stale or partial `.build` is the class in `Notes/solutions/2026-11-10-skip-build-after-a-failed-build-runs-the-old-tests.md`; a checkout gives every file a new mtime, which can make SwiftPM rebuild everything anyway; the repository cache limit (10 GB) evicts | Measure first: one experiment job that restores `.build` and records the build time on a PR push |
| 6 | **Run the three encodings of an e2e-game leg in parallel** (three servers on three ports) | about 3 min of a leg's 5.5 | Medium: port and log collisions, CPU contention on a 2-core runner, interleaved output | Only if lever 1 isn't enough |
| 7 | **Share one build across the env-only variants** (build once, then `swift test --skip-build` per variant) | runner minutes (about 3 builds × 4 min), **no wall clock**: the runs would be serial | Low if each run is gated on a build that completed, per the skip-build lesson | Worth it only if runner minutes start to matter |

**Local Mac:**

| # | Change | Saves | Risk |
|---|---|---|---|
| L1 | Keep a warm worktree per long-lived line of work instead of a fresh one per run: a fresh worktree costs a cold build (313.89 s debug) | about 5 min per avoided cold build | None |
| L2 | Log each take and release of the local build lock, so waits can be measured | nothing directly; it turns the two observations into data | None |

## Proposed order

Each workflow change is its own PR, measured on its PR's CI against the medians above:

1. Levers 1 and 2 together: two job definitions, and the largest saving. Expected e2e-game about 11 min, examples about 8.
2. Lever 3, with the clean step removed or narrowed.
3. Lever 4 (#466), in `Examples/` and its tests.
4. Lever 5 only as an experiment first: one job that restores `.build` and reports the build time. Adopt it only if a PR push saves more than a minute and the tests then pass from a clean build too.
5. Levers 6 and 7 only if the numbers after 1–3 call for them.

Expected after 1–3: a push completes in about 10–11 minutes instead of about 18.

## What would change the ranking

- If the in-turn sync switch goes away (layer 3 PR B in `2026-11-05-layer3-prs.md` removes the legacy sync path), e2e-game and build lose their `false` legs, and lever 1 costs half as many extra jobs.
- If runner minutes start to count (a private repository, or a concurrency limit hit), lever 7 rises.
