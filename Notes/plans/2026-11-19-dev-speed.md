### Build variants: one binary, different steps

The Swift test jobs select their variant through environment variables only:

| Job | Variables | Its own steps |
|---|---|---|
| build (in-turn sync true / false) | `IN_TURN_SYNC` | the lessons lint, the clean step, the must-not-compile snippets, the full `swift test`, the wall-clock tests |
| sync-tables-off | `USE_SYNC_TABLES=false`, `TYPED_LEAF_VALUES=false` | the full suite, then greps that check pinned tests ran |
| per-player-sync-tables-off | `PER_PLAYER_SYNC_TABLES=false` | only the Transport and NIO test targets |

Each variable is read at run time through `EnvKeys` / `TransportEnvKeys`. `Package.swift` defines no compile-time flags. The conditional compilation in `Sources/` is `#if DEBUG` plus platform constants (`canImport(Glibc)` / `Musl` / `Darwin`, `os(macOS)`, `canImport(Foundation)`), which are the same for every job on the same image. So every variant could run the same debug binary, while keeping its own steps and filters. Today each job builds it again from nothing: cold, with dependency resolution, about 4 to 5 minutes of each job. Seven jobs build Swift code from a clean checkout this way, plus the two e2e-game legs. No job caches `.build` or the package checkouts. `actions/cache` is used for npm only.

### The clean step in build-and-test.yml

`rm -rf .build` and `swift package clean` came in with 94bada97 (2026-01-17), whose message gives two reasons: "Clean .build directory before building to avoid cache corruption" and "Remove -v flags to reduce output that may trigger internal errors" (the `invalidPayloadSize` errors in its title). On a fresh runner with a fresh checkout there is no `.build` to clean or corrupt, so the step does nothing and costs nothing today. It matters only once a cache restores into `.build`: then `rm -rf .build` would throw the cache away.

## Levers, ranked

Minutes are the push's wall clock unless marked as runner minutes. Today's critical path is e2e-game (17.9). After it come examples (13.0) and build (10.8).

| # | Change | Saves per push | Risk |
|---|---|---|---|
| 1 | Split e2e-game's row-addressing-off step into its own matrix legs | **about 5 min** | Low |
| 2 | Move the deep-research Python tests out of `examples` into their own job | **about 2 min, with lever 1** | Very low in the same image |
| 3 | Cache SwiftPM's dependency checkouts | about 1 min on every Swift job | Low |
| 4 | Fix the open flake classes, by cost | about 0.75 min on average, and the reruns' attention | Low each |
| 5 | Cache `.build` of our own code | up to 3–4 min a job on a hit; unknown on a PR push | Medium |
| 6 | Run the three encodings of an e2e-game leg in parallel | about 3 min of a leg's 5.5 | Medium |
| 7 | Share one build across the env-only variants | runner minutes only | Low |

### 1. Split e2e-game's row-addressing-off step

The matrix becomes in-turn sync × row addressing: 4 legs instead of 2. e2e-game drops to about 11 min, and examples (13.0) becomes the critical path.

- Each leg runs the same steps and checks. Each step already writes its own `E2E_TMP_DIR`.
- **Coverage goes up.** Today the rows-off step is skipped whenever the main step fails; as its own leg it runs regardless.
- The matrix renames the jobs. Nothing requires them by name.
- `fail-fast: false` stays.
- Cost: about 2 × 5 runner minutes for the two extra builds.

### 2. Move the deep-research Python tests into their own job

With lever 1 this saves about 2 min: examples drops to about 8 min, and e2e-game at about 11 is the critical path again. Alone it saves nothing. Moving the step also shrinks #484's cost: a hang then reruns a job of a few minutes, not the 13-min `examples`.

The facts:
- The step runs 26 test files.
- 18 of them use `subprocess`: `git rev-parse`, `check-ignore` and `cat-file`, temporary and shallow repositories, `node` through `runmeta`, and stub executables on `PATH`.
- None runs the real `swift`. Where `swift` appears, it is a stub the test writes.
- They need full history (`fetch-depth: 0`), `git` with `safe.directory` set for the workspace, `python3` and `node` 20.

The new job's environment, two options:

- **(a) The same image (recommended).** `container: swift:6.2.4-noble`, `scripts/ci-apt-install.sh python3` (Ubuntu 24.04's Python 3.12, git 2.43.0 as today), `actions/setup-node` 20, checkout with `fetch-depth: 0`, the same `safe.directory` line. It is the step moved unchanged.
  - Risk: very low.
  - Costs: an image pull, and it keeps the apt exposure.
- **(b) The plain runner.** `ubuntu-22.04` without a container: its system Python is 3.10, so `actions/setup-python` with 3.12 and `actions/setup-node` with 20, the same checkout depth, and `safe.directory` kept for parity.
  - This removes the apt step and the image pull.
  - Risk: low to medium. The runner's git version and the Python patch level differ from today's, and a test that passes on one can fail on the other.

Either way, the PR shows the new job's `26 deep-research test files run` line and each file's test count, equal to the old step's on the same commit.

### 3. Cache SwiftPM's dependency checkouts

This saves about 1 min on every Swift job, on the critical path too.

- **What to cache:** SwiftPM's shared cache, `.cache/org.swift.swiftpm` under the container's `$HOME` (`/github/home` in a container job), not `.build/checkouts`. The first run's log confirms where SwiftPM writes it.
- **Key:** the image, `Package.resolved`, and the OS and architecture. The job runs inside the container and can't ask Docker for the image digest, so pin every `image:` line in the workflows to the same digest and put that string in the key. The toolchain stays 6.2.4 at that digest; the digest is recorded wherever performance results record the image.
- **Scope:** a PR's run writes only to its own ref's cache. A PR reads its own ref and `main`'s. `main` reads only its own, written only by runs on `main`, so no PR (from a fork or not) can change what `main` restores. Save only on success, with `actions/cache/restore` and `actions/cache/save` under `if: success()`.
- **The clean step:** drop `rm -rf .build` and keep `swift package clean`. The cache lives outside `.build` anyway.
- **Risk:** low. SwiftPM checks out the pinned revisions from the cached clones, and a miss costs what today does.

### 4. Fix the open flake classes, by cost

In the order of the table above:

1. **#484**, the deep-research hang. Lever 2 also cuts its cost.
2. **#577**, `test-join-supersede`.
3. **#466**, `LoadTestPacingTests`.
4. **#488**, `closeSessionAfterQueuedFrames`.
5. **#482**, `run()` returns before `.stopped`.

Then #614 (the per-player 40-min hang), filed with this plan. Each fix is its own change. The Swift races (#577, #488, #482) get a hold at the `await` (`HoldPoints`, `TestGate`), not a longer timeout. #484 gets an event or a subprocess timeout in its Python test.

The apt outage isn't a test flake. Lever 2(b) removes one apt step. Checking whether the image already ships `curl` (and skipping the install if so) is a cheap probe, not yet checked.

**#466's clock.** `LoadTestPacing` takes an injected clock with the contract of the tick loop's `TickLoopClock` (and the turn clock #608 adds): `now`, and a `sleep(until:)` that returns early when the task is cancelled; the test advances a manual clock.
- No third clock shape. Because `TickLoopClock` is `package` in `SwiftStateTree` and `Examples/GameDemo` is another package, the tool declares its own type with that same shape.
- The production path keeps `ContinuousClock` and today's sleep.
- The `startLag` the tool reports stays real elapsed time: the load-test tools are measurement tools, and only the tests run on the manual clock.

### 5. Cache `.build` of our own code

The key is the same as lever 3's, plus the sources, with **no `restore-keys` prefix**: only an exact hit restores. It could save up to 3–4 min a job on a hit; the saving on a PR push, where the sources changed, is unknown.

- **Risk: medium.**
  - A stale or partial `.build` is the class in `Notes/solutions/2026-11-10-skip-build-after-a-failed-build-runs-the-old-tests.md`.
  - A checkout gives every file a new mtime, which can make SwiftPM rebuild everything anyway.
  - The repository's cache limit (10 GB) evicts.
- **Safeguards:** if the build fails after a restore, the job removes `.build` and builds clean in the same job. It never runs `--skip-build` after a failed build.
- **Measure first:** one experiment job that restores `.build` and records the build time on a PR push.

### 6. Run the three encodings of an e2e-game leg in parallel

Three servers on three ports, saving about 3 min of a leg's 5.5. Risk: medium, from port and log collisions, CPU contention on a 2-core runner, and interleaved output. Only if lever 1 isn't enough.

### 7. Share one build across the env-only variants

Build once, then run each variant's own steps with `swift test --skip-build`, each gated on a build that completed (the skip-build lesson). This saves runner minutes (about 3 builds × 4 min) but **no wall clock**, since the runs would be serial. Worth it only if runner minutes start to matter.

## Proposed order

Each workflow change is its own PR, measured on its PR's CI against the medians above:

1. **Levers 1 and 3 together.** The largest saving, plus the checkout cache, with the clean step narrowed. Expected: e2e-game about 10 min, and examples (13.0) becomes the critical path.
2. **Lever 2, option (a).** Expected: examples about 8 min, and a push completes in about 10–11 min instead of about 18.
3. **Lever 4,** one fix per issue, starting with #484 and #577. #466 lives in `Examples/` and its tests.
4. **Lever 5 as an experiment only:** one job that restores `.build` and reports the build time. Adopt it only if a PR push saves more than a minute and the tests then pass from a clean build too.
5. **Levers 6 and 7** only if the numbers after 1–3 call for them.

## What would change the ranking

- If the in-turn sync switch goes away (layer 3 PR B in `2026-11-05-layer3-prs.md` removes the legacy sync path), e2e-game and build lose their `false` legs, and lever 1 costs half as many extra jobs.
- If runner minutes start to count (a private repository, or a concurrency limit hit), lever 7 rises.
