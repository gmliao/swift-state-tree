# Transport

Transport layer connects network connections with LandKeeper, with the core goal of "not exposing network details to Land DSL".

## Design Focus

- Land layer only cares about `LandContext` and handlers, doesn't know WebSocket/HTTP details
- Transport layer is responsible for connection management, message serialization, and routing
- Synchronization uses snapshot + diff to avoid blocking state mutation

## Data Flow

```
Client ↔ WebSocketTransport ↔ TransportAdapter ↔ LandKeeper
```

## Three-Layer Identification

- `playerID`: Account/player identity (business layer)
- `clientID`: Device or client instance (provided by application)
- `sessionID`: Connection layer identification (generated by server)

These three layers of identification enter `LandContext`, giving handlers a consistent interface,
and supporting multi-device, multi-connection behavior control.

## Core Components

- Transport protocol: Abstract connection behavior (start/stop/send)
- WebSocketTransport: Default WebSocket implementation
- TransportAdapter: Parse messages and call LandKeeper
- LandManager / Registry: Manage multiple rooms
- LandRouter / LandRealm: Cross-room routing and control

For integrating SwiftStateTree with another HTTP/WebSocket framework (e.g. Vapor, Kitura), see [Server Integration Guide](server-integration.md). For JWT validation, guest mode and the admin API key, see [JWT and Guest Mode](auth.md).

## Join and Session Flow

- Client must explicitly send join request
- Join creates `PlayerSession` and executes `CanJoin` / `OnJoin` in order
- Initial join returns snapshot, subsequent updates use `StateUpdate` (firstSync/diff)
- Targeted events (to the session, client or player) sent while the session is still joining are held, and delivered right after its firstSync, in emission order. Broadcast events aren't held: the firstSync already reflects them. This holds with in-turn sync on (`IN_TURN_SYNC`, the default).
  - At most 256 events / 256 KiB are held per joining session (`JOIN_HELD_EVENTS_MAX`, `JOIN_HELD_EVENTS_MAX_BYTES`). Over that, the join fails with `JOIN_EVENT_OVERFLOW` and the session is closed; the client reconnects to a fresh state.
  - Held events describe effects that are already in the firstSync. Server events are notifications, and the synced state is the source of truth: a client that applies events as deltas to its own state would count them twice.
- Frames the client sends while its join completes (actions, client events), before or right after the JoinResponse, are applied after OnJoin, in the order sent. With in-turn sync on, they wait until the JoinResponse and firstSync have been sent, then run one at a time; later frames queue behind them.
  - At most 256 frames / 256 KiB wait per session (`JOIN_DEFERRED_INBOUND_MAX`, `JOIN_DEFERRED_INBOUND_MAX_BYTES`). Over that before the join completes, it fails with `JOIN_INBOUND_OVERFLOW`; after it, while the earlier frames are still being applied, the session gets `INBOUND_OVERFLOW`. Either way the session is closed, since the client lost a frame it sent: it reconnects and joins again.
- The join errors that close the session (`JOIN_INBOUND_OVERFLOW`, `INBOUND_OVERFLOW`, `JOIN_EVENT_OVERFLOW`, and a timed-out or failed join's `JOIN_DENIED`) are written to the connection before it is closed, waiting at most `FINAL_FRAME_CLOSE_TIMEOUT_MS` (default 1000). That is the order of the hand-off: a client that stopped reading may still not receive the error. A custom `Transport` without `closeSessionAfterQueuedFrames` closes at once, which can drop the error.

### Connections

- **One `SessionID` per connection.** Every per-session map in the transport, router and adapter is keyed by it, so a caller of `WebSocketTransport.handleConnection` passes a fresh ID for each connection (the NIO server makes a UUID per connection).
- `handleConnection` rejects a connection whose ID is still held: connected, being disconnected (until the delegate's cleanup returns), or closed by the server and not yet confirmed. It returns `.rejected(.sessionIDInUse)`, closes the connection, never calls `onConnect`, and counts `connectionsRejectedSessionIDInUse`. After a rejection the caller must not call `handleIncomingMessage` or `handleDisconnection` for that connection: both would act on the session that holds the ID.
- **Serial delivery per session.** A session's frames reach `TransportDelegate.onMessage` one at a time, each after the previous call returned (the NIO server's inbound chain does this). The join's frame deferral relies on it.

PlayerSession field priority:

1. join request content
2. JWT payload
3. guest session

## Synchronization Model

- snapshot: Complete state (including per-player filtering)
- diff: Only send changes (path-based patches)
- firstSync: Sent once after player's cache is first established

### Broadcast vs Per-Player Updates

Frames per session and sync cycle, in this order (the outbound writer keeps it):

- **opcodeMessagePack**: the merged broadcast frame (opcode **107**: the broadcast diff, encoded once for all sessions, plus the broadcast events), then the session's targeted event frames, then its per-player state frame (opcode 0/1/2). A 107 frame is sent only when the broadcast diff is non-empty or events are queued; a cycle that changes only per-player state sends the per-player frame alone.
- **jsonObject / opcodeJsonArray**: one combined state frame per session. Events are not merged; each is sent when emitted.
- **firstSync**: a single combined update (the player's full state).

Late joiners (#189): with merged broadcast frames, the broadcast dynamic-key table is shared by the land's sessions. When a joiner's firstSync has committed after a 107 frame with state patches, the next cycle resets the key scope for every member: its frame is typed firstSync and redefines the keys it uses, so the joiner never sees a slot defined before it joined. This costs about 13 bytes per member on the first sync after each join, plus one redefinition of each key; there is no reset while the broadcast table is empty, or when the encoder keeps no key tables (dynamic-key compression or path hashing off).

## Error Handling

- join/action/event errors return `ErrorPayload`
- Join checks landID and session state to avoid duplicate joins or incorrect routing

## Multi-Room Support

- `LandManager` manages Land lifecycle and queries
- `LandRouter` routes connections to corresponding land
- In multi-room mode, join routes based on landType + instanceId

## WebSocket Path for LB / K8s

Server accepts both:
- `/game/{landType}` (e.g. `/game/hero-defense`)
- `/game/{landType}/{instanceId}` (e.g. `/game/hero-defense/room-abc`) — for path-based routing

Client must send Join with `landID: "landType:instanceId"`. See [Deploy & LB](../deploy/README.md).

## State Update Encoding

| `TransportEncodingConfig` | Message | State update | Default where |
|---|---|---|---|
| `.json` | `json` | `jsonObject` | `NIOLandServerConfiguration.transportEncoding`; DemoServer (`TRANSPORT_ENCODING=json`) |
| `.jsonOpcode` | `json` | `opcodeJsonArray` | `TRANSPORT_ENCODING=jsonOpcode` |
| `.opcode` | `opcodeJsonArray` | `opcodeJsonArray` | `TRANSPORT_ENCODING=opcode` |
| `.messagepack` | `messagepack` | `opcodeMessagePack` | GameServer (`TRANSPORT_ENCODING=messagepack`); recommended for production |

`TransportEncodingConfig(message:stateUpdate:)` itself defaults to `json` messages with `opcodeJsonArray` state updates; dynamic-key compression is on by default in every opcode state-update encoding with path hashes. Both example servers read `TRANSPORT_ENCODING` (`json`, `jsonOpcode`, `opcode`, `messagepack` or `msgpack`, case-insensitive); an unknown value falls back to `json`.

### Atomic values

A type that adopts `AtomicSnapshotValue` (`IVec2`, `IVec3`, `Position2`, `Velocity2`, `Acceleration2`, `Angle`, a user struct declared with `@SnapshotConvertible(atomic: true)`) is one value in the diff, never diffed per leaf. Only the declaration makes a type atomic; a struct that merely has an `{x, y}` shape is diffed field by field.

- **Opcode state updates** (`opcodeJsonArray`, `opcodeMessagePack`) send an atomic value as the array of its leaves, in the schema's `leafOrder`: a `Position2` is `[x, y]`, an `Angle` is `[degrees]`, with fixed-point integers. This holds wherever the value sits: a field, an element of an array, a map value, an optional, a struct inside any of these, and inside an added object or a firstSync snapshot. In MessagePack a `Position2` patch value is 11 B instead of 18 B, an `Angle` 6 B instead of 14 B.
- **`jsonObject` state updates and server events stay keyed** (`{"v": {"x": ..., "y": ...}}`).
- **The logical form is unchanged:** `StatePatch`, `SnapshotValue`, the state hash and the sync-output hashes are keyed, so records and their verification don't depend on the wire form.
- **The switch:** `TransportEncodingConfig.atomicValues` is `.positional` by default; `.keyed` (`withAtomicValues(.keyed)`) sends keyed values in opcode state updates too, for one release, for clients that can't be updated with the server.
- **The schema declares the form:** the schema root carries `"x-stateTree": {"atomicEncoding": "positional"}`, and each atomic definition its `leafOrder`. Both are in the schema hash. The marker states what a client must be able to decode, so it reads `positional` under `.keyed` too. The SDK view decodes positional and keyed values, refuses a schema whose `atomicEncoding` it doesn't know, and accepts a schema without the marker.
- **Schema hash and old clients:** a client built before positional atomic values has a different schema hash. With `expectedSchemaHash` on, it is refused at join, instead of keeping `[x, y]` as a plain array. A deployment that runs `.keyed` for such clients keeps `expectedSchemaHash` off until they are updated. The SDK in this repository ships with the server: update both together.
- A value at an atomic path whose keys aren't exactly its declared leaves can't be encoded; the patch goes through the adapter's unencodable-patch path instead of being sent.

### Path index

With `TransportEncodingConfig.pathIndex` on (the default; `withPathIndex(false)`, or `PATH_INDEX=false` on the Demo and Game servers, turns it off), an opcode state update with path hashes sends each patch's pattern as its **path index** instead of its 32-bit hash. The path index is the hash's position in the land's schema `pathHashes` values, de-duplicated and sorted ascending (`PathHasher.sortedHashes`).

- **Smaller ids:** a land with fewer than 128 patterns has 1-byte indices in MessagePack (a hash takes 5 B), and 1–3 digits in JSON (a hash 9–10).
- **Same schema:** server and client derive the table from the schema they share. The schema, its hash and the codegen output don't change.
- **On by default.** The SDK and the load tools declare `pathIndex` at join. A client that doesn't is refused while the server has it on.
- **Without path hashes** the opcode encoders send string paths, so the index is off in effect (`effective(pathHashes:)`) and isn't required of clients.
- **A path outside the schema** has no index, so that patch can't be sent. The adapter's unencodable-patch handling applies, as for an invalid atomic value: the patch is dropped, the rest of the update is sent, the scope is marked unverifiable in the sync stream, and the field reaches the client again on its next change. `TransportAdapter.unmappedPathPatches` counts the dropped patches, and each new pattern is logged once.
- **Records stay logical:** the index is chosen in the encoder, after the sync plan. Records, the sync-stream hashes and the sync-output goldens don't change.

**The handshake.** The schema hash doesn't change, so an old client would read indices as hashes. A client declares the state-update features it decodes in its join metadata, next to `schemaHash`: `"stateUpdateFeatures": ["pathIndex"]`.

- A server with the index on refuses a join that doesn't declare it, with `JOIN_STATE_UPDATE_FEATURE_MISSING` and `unsupported state update encoding: missing pathIndex`. The router checks this before it looks up or creates a land.
- `joinResponse` echoes the features in use (`stateUpdateFeatures`), and the client decodes by them. It is absent when none is on.
- With the index off, a client that declares nothing joins as before. A client that declares more than the server uses is fine.
- The SDK in this repository declares `pathIndex`, `fieldMerge`, `syncSequence` and `rowAddressing` (`SUPPORTED_STATE_UPDATE_FEATURES`), as does a Swift client with `StateUpdateFeature.joinMetadata`. `Tools/CLI` decodes through the SDK. The `ws-loadtest` client declares `pathIndex`, `fieldMerge` and `syncSequence` in every join, not yet `rowAddressing`.

### Field merge

With `TransportEncodingConfig.fieldMerge` on (the default; `withFieldMerge(false)` or `FIELD_MERGE=false` on the Demo and Game servers turns it off), an opcode state update with path hashes sends the patches of one frame that set (or add) fields of one parent with the same dynamic keys as **one merged entry**: `[parentId, dynamicKey, op, fieldMask, v1, v2, …]`.

- **op** is 4 (each field set) or 5 (each field added). **parentId** is the parent's path id: its hash, or its path index with `pathIndex`.
- **The mask:** a field's bit is its rank among the parent's named children (patterns `parent.<name>`, name not `*`), sorted by name in UTF-8 byte order. The values follow in ascending bit order, one per set bit. A mask of bits 0–6 is a 1-byte MessagePack fixint.
- **Mergeable fields** are leaves and atomic values (`FieldMergeTable`). A field with rank 32 or above, a delete, a set of an object with fields below it, and a path outside the schema stay plain entries. The mask is 32 bits because a JavaScript client reads integers exactly only up to 2^53, and its bitwise operators are 32-bit.
- **Order:** a merged entry takes the place of its first member. A patch at, above or below the parent's path (a delete or set of the entity, a replace of its map, a delete of a sibling field) closes the group, so the fields after it start a new entry and are applied after it, as in the plain frame. A patch to another entity doesn't close it.
- **Records stay logical,** as with the path index: merging happens in the encoder, after the sync plan.
- **The handshake:** a server with the merge on requires `fieldMerge` in the join's `stateUpdateFeatures`, the same way as `pathIndex`; the missing list names every feature missing (`missing pathIndex, fieldMerge`). Without path hashes the merge is off in effect.

### Row addressing

With `TransportEncodingConfig.rowAddressing` on (default off; `withRowAddressing(true)`, or `ROW_ADDRESSING=true` on a server that builds its config with `TransportEncodingConfig.rowAddressingFromEnvironment()`), an opcode state update names the rows of a slot-addressed table by a **slot**, not by their key. A slot-addressed table is a broadcast field at the root that maps keys to state nodes (`[String: Unit]`).

- **The entries** (`RowPatchOpcode`):
  - create `[tableId, slot, 6, generation, null, key, value]`: a new row, whole; the slot is bound to the key from then on;
  - delete `[tableId, slot, 7]`: the row and everything below it is removed, and the slot is free;
  - column set `[leafPathId, [slot, …], 8, [value, …]]`: one leaf set in those rows, slots ascending;
  - column clear `[leafPathId, [slot, …], 9]`: one leaf removed in those rows.
  - **tableId** is the path id of the row's pattern (`units.*`), **leafPathId** that of the leaf (`units.*.hp`). Every other patch keeps today's form, in the same frame.
- **Slots and generations:** a freed slot is taken again by a later create, with the next generation. A client refuses an entry for an unbound slot, a create on a bound slot, a create whose generation isn't above the slot's last one, and any slot, op or generation that isn't an exact integer in range.
- **A first view** (a joiner's, or a resync's) sends each slot-addressed table as `{}` followed by one create per row, so the client learns every binding.
- **A row that doesn't encode** (a non-finite number in opcode JSON) is dropped from the frame whole: its create, its column members and every patch below it. The rest of the table is sent, and the row is diffed again next sync until it goes out. The dropped scope is unverifiable in the sync stream.
- **Records stay logical:** row entries are made in the encoder, after the sync plan, so the record and the sync-stream hashes are the same with the feature off or on.
- **In effect** only with path hashes, `pathIndex`, `syncSequence`, an opcode encoding, the delta strategy, in-turn sync (the default) and joins through the router (`LandManager` with a shared transport, as NIO hosting does). Otherwise it is off, with a warning. It turns the sync tables on (`USE_SYNC_TABLES`), which hold the slot tables. A replay land never uses it.
- **The handshake:** a land with row addressing in effect refuses a join that doesn't declare `rowAddressing`, with `JOIN_STATE_UPDATE_FEATURE_MISSING`, after the land lookup. The TypeScript SDK and a Swift client with `StateUpdateFeature.joinMetadata` declare it; the `ws-loadtest` client doesn't yet.
- **A broken rule closes the connection (TypeScript SDK).** A row entry the client refuses (above), or a row entry when `rowAddressing` wasn't negotiated, means the client's view can no longer be trusted. The SDK closes the connection with **4013** (`invalidRowEntry`, sent by the client, reason `row entry: <rule>`, at most 123 UTF-8 bytes) instead of dropping the frame:
  - each view's `onError` gets source `'decode'`, code `INVALID_ROW_ENTRY` and `details.rule`;
  - frames still queued on the connection are dropped, not applied, and counted in `decodeErrorStats().droppedAfterStrictClose`;
  - the close then destroys the views and calls `onDisconnect`, as any close does. The SDK doesn't rejoin; a rejoin starts from a fresh firstSync.
  - A custom WebSocket factory (`registerWebSocketFactory`) must pass `close(code, reason)` through to its socket: one that ignores the arguments closes with 1005 (no status), and the server never sees 4013.

  A join response with `rowAddressing` but without `pathIndex` closes the same way, and the join is refused. Other decode errors (a dynamic-key slot used before its definition) still drop the frame and go on, and after `disconnect()` an error is only counted. The Swift `SessionClose.Code` reserves 4013 for this close. Both decoders take an integral literal such as `7.0` or `1e2`. The difference is a literal within a double's rounding of an integer, such as `7.0000000000000000001`: the Swift decoder refuses it, while `JSON.parse` has already rounded it to 7 before the SDK sees it, so the SDK takes it. That is a limit of JavaScript's number parsing. The encoders never write such a literal.
- **Row tables (TypeScript SDK)** are per connection: started again at open, at every join response (a rejoin on the same socket gets creates for the slots the last land bound) and at every resync, not at a key-scope reset. After a resync, the frame with the resync's sequence still applies its row entries and every patch under a root that had a bound row when the resync was applied: the snapshot holds those tables as committed, not live. Its other patches are skipped, as without row addressing.


A frame's bytes depend only on its content, not on dictionary iteration order, which Swift seeds per process. Every state update the adapter sends has its patches in one canonical order, set before field merge and dynamic-key slots are planned. (An encoder used on its own, from `makeStateUpdateEncoder` or a custom one, keeps the order it is given.)

- **Tables:** every `StateNodeProtocol` type reachable from the land's state is a table, numbered parents first (the root is 0), ties in the order a depth-first walk over fields in UTF-8 name order first meets them. Recursive state types (which schema generation refuses) still get a deterministic order, but the tables on a cycle and below it come last, so a parent's table can follow its child's.
- **A patch's key** is `(table, chain, field, sub-key path)`: the table of the row it addresses, the row's `(field, key)` pairs from the root, the field it writes (none for a set or delete of the row itself), and the components below that field. Keys compare table first, then component by component in UTF-8 byte order, a prefix first, so a row's own patch comes before its fields'.
- **Object keys:** JSON state updates and JSON transport messages write object keys sorted (`JSONEncoder` `.sortedKeys`, UTF-8 byte order); MessagePack maps pack string keys in UTF-8 byte order, then any other key by its packed bytes (two keys with the same bytes, such as `.int(1)` and `.uint(1)`, keep no fixed order between them).

The diff never puts a path and its ancestor in one frame, so sorting doesn't reorder dependent patches. Clients apply a frame's patches in the order received and need no change.

State updates are encoded serially per sync cycle. Per-player updates within a room are encoded one after another; for multi-room scenarios, each `TransportAdapter` manages one room independently.

## Environment Variables

Transport-related behavior can be tuned via environment variables. All variables are read at `TransportAdapter` init time. The complete list and parsing rules are documented in `TransportEnvConfig` (SwiftStateTreeTransport module).

| Variable | Type | Default | Description |
|----------|------|---------|-------------|
| `ENABLE_DIRTY_TRACKING` | Bool | init param | Enable dirty-field tracking for smaller diffs; disable for high-update-ratio scenarios |
| `USE_SNAPSHOT_FOR_SYNC` | Bool | true | Use one-pass snapshot extraction; set to `false` for legacy separate broadcast + per-player path |
| `USE_SYNC_TABLES` | Bool | false | Experimental: diff broadcast fields on the typed sync tables instead of snapshots (delta strategy only). The frames are the same bytes either way. See [Sync](../core/sync.md#rules-for-synced-value-types) for the rules a synced value type must follow |
| `SYNC_STRATEGY` | String | `delta` | `delta` sends changed fields only; `full-snapshot` sends each recipient's complete view every sync (measurement baseline, not a production mode) |
| `ENABLE_CHANGE_OBJECT_METRICS` | Bool | false | Log changed-vs-unchanged object ratio of the measured syncs (see `AUTO_DIRTY_SAMPLE_EVERY`) |
| `CHANGE_OBJECT_METRICS_LOG_EVERY` | Int | 10 | Measured syncs between change-object metric logs |
| `CHANGE_OBJECT_METRICS_EMA_ALPHA` | Double | 0.2 | EMA alpha for change rate per sync (0.01–1.0); scaled to the sample interval |
| `AUTO_DIRTY_TRACKING` | Bool | true | Auto-switch dirty tracking based on change rate hysteresis |
| `AUTO_DIRTY_OFF_THRESHOLD` | Double | 0.55 | EMA threshold to switch dirty tracking OFF |
| `AUTO_DIRTY_ON_THRESHOLD` | Double | 0.30 | EMA threshold to switch dirty tracking ON |
| `AUTO_DIRTY_REQUIRED_SAMPLES` | Int | 30 | Consecutive syncs past a threshold before mode switch (rounded up to whole samples) |
| `AUTO_DIRTY_SAMPLE_EVERY` | Int | 1 | Measure the change rate on one sync in N (clamped to 1–1024); 1 measures every sync. Above 1 the samples are at a fixed phase, so a workload whose busy syncs repeat with a period dividing N is always measured at the same point |
| `TRANSPORT_PROFILE_JSONL_PATH` | String | (disabled) | When set, enables transport profiling and writes JSONL to this path |
| `TRANSPORT_PROFILE_INTERVAL_MS` | Int | 1000 | Profiling write interval in ms (min 100) |
| `TRANSPORT_PROFILE_SAMPLE_RATE` | Double | 0.01 | Latency sample rate (0.001–1.0) |

- `PATH_INDEX` (Bool, default true): opcode state updates with path hashes send path indices instead of hashes. See [Path index](#path-index). - `FIELD_MERGE` (Bool, default true): opcode state updates with path hashes merge the field patches of one parent into one entry. See [Field merge](#field-merge). Read only by servers that build their encoding config with `TransportEncodingConfig.fieldMergeFromEnvironment()` (the Demo and Game servers do), and by `EncodingBenchmark` (`--field-merge on|off`).
- `ROW_ADDRESSING` (Bool, default false): opcode state updates name the rows of root node maps by slot. See [Row addressing](#row-addressing). Read by servers that build their encoding config with `TransportEncodingConfig.rowAddressingFromEnvironment()`, as the Demo and Game servers do. It takes effect only on lands with path hashes (GameServer's), and CI runs the GameServer E2E suite with it on in both opcode encodings.
- `SYNC_LAG_RESYNC_MS` (default 3000), `SYNC_ACK_FRESHNESS_MS` (2000), `SYNC_ACK_TIMEOUT_MS` (10000), `SYNC_LAG_SLOW_CONSUMER_COUNT` (3) and `SYNC_LAG_SLOW_CONSUMER_WINDOW_MS` (60000) (Int; `SyncLagPolicy.fromEnvironment()`, the default of `NIOLandServerConfiguration.syncLag` and of a `TransportAdapter` built without a policy): the sync-lag thresholds. A missing, non-integer or non-positive value gives the default.
- `SYNC_LAG_CLOSE_GRACE_MS` (Int, default 2000; `SyncLagPolicy.closeGrace`): the close grace of the 4010, 4011 and 4012 closes. 0 turns it off; a non-integer or negative value gives the default.
- `WS_PONG_TIMEOUT_MS` (Int, default 20000; NIO hosting, `NIOWebSocketServerConfiguration.pongTimeout`): the server pings each WebSocket session every 30 s, each session at its own phase. If no frame arrives from the peer within this many milliseconds after a ping (a pong or any message counts), the server closes the connection with 1001 (going away). The clock starts when the ping is written, so a ping queued behind a slow reader's backlog counts too. Must be positive and below 30000; other values give the default.
- `WS_SEND_BACKLOG_MAX_BYTES` (Int, default 8388608 = 8 MiB) and `WS_SEND_BACKLOG_MAX_UNWRITABLE_MS` (Int, default 30000; NIO hosting, `NIOWebSocketServerConfiguration.sendBacklogBound`): the send backlog bound (#61). See [Send backlog bound](#send-backlog-bound). 0 disables that bound; a negative or non-integer value gives its default, with a warning.
- `WS_INBOUND_BACKLOG_MAX_MESSAGES` (Int, default 1024) and `WS_INBOUND_BACKLOG_MAX_BYTES` (Int, default 4194304 = 4 MiB; NIO hosting, `NIOWebSocketServerConfiguration.inboundBacklogBound`): the inbound backlog bound (#113). See [Inbound backlog bound](#inbound-backlog-bound). 0 disables that bound; a negative or non-integer value gives its default, with a warning.
- `IN_TURN_SYNC` and `LAND_LOOP_PHASE_OFFSET` (runtime, default on): see [Runtime](../core/runtime.md#in-turn-sync-default).
- `RESOLVER_TIMEOUT_MS` (Int, default 5000) and `RESOLVER_INIT_TIMEOUT_MS` (Int, default 30000; runtime): the deadline on one resolver group, and on OnInitialize's; 0 disables it. See [Resolver deadline](../core/resolver.md#deadline).
- `ACTION_IN_FLIGHT_MAX_PER_SESSION` (Int, default 8) and `RESOLVER_ABANDONED_ACTIONS_MAX` (Int, default 256; runtime): the caps on one session's actions in their resolvers and on the process's abandoned ones; 0 removes a cap. See [Actions with resolvers](../core/resolver.md#actions-with-resolvers).
- `JOIN_TIMEOUT_MS` (Int, default 12000; 0 disables it; a negative or non-integer value gives the default): the end-to-end join budget (#104). It runs from the join request and covers the land lookup or creation and the wait in the land's membership queue, until the keeper's join starts; for a join that completes in a turn, the flip then waits for what is left of it. A join out of budget gets `JOIN_DENIED` "Join timed out", followed by the phase (`during land lookup`, `waiting for admission` or `waiting for the flip`), as its last frame, and its session is closed; a retry is a new connection. Keep the client's join timeout above it (the CLI's is 15 s, `CLI_JOIN_TIMEOUT_MS`), so the client hears the error first. A join through `TransportAdapter.performJoin` without the router gets the budget from its admission, for the flip wait.
  - **A started keeper join isn't bounded by the budget** (#241). The timeout acts only on an admission that hasn't started. One already in the keeper's join is left to finish, since cutting it would break the membership queue's order. Its own bound is the resolver deadlines: CanJoin, the OnLeave of a replaced session of the same player, and OnJoin, each group up to `RESOLVER_TIMEOUT_MS` (5 s), so up to 15 s. On a land's first join, the keeper's join also waits for the land's initialization, up to `RESOLVER_INIT_TIMEOUT_MS` (30 s). The worst case is therefore the time spent before the keeper's join started (less than the budget), plus 15 s, plus 30 s on a first join, which is more than the CLI's 15 s. After a started join, the in-turn flip waits for what is left of the budget, which may be nothing; the legacy path has no flip wait.
  - **The flip's own timeout is a lower bound.** It goes through the land's membership queue, so work queued ahead of it can delay it.
  - **Other closes can come first.** Once a join is admitted, the session can also be ended before the flip wait finishes: by `JOIN_INBOUND_OVERFLOW`, when the client sends more than the join's inbound bound while it waits, or by the keepalive pong timeout (`WS_PONG_TIMEOUT_MS`, close code 1001), which sends no error frame. A client therefore doesn't always see `JOIN_DENIED` for a join that didn't complete.
- `JOIN_FLIP_TIMEOUT_MS` (deprecated, to be removed): set `JOIN_TIMEOUT_MS` instead. When set, it still caps the flip wait inside the budget, and the router logs a deprecation warning.
- `LAND_LIFECYCLE_LOG_PATH` (String, default unset: no log): a file where every `LandManager` appends one JSON line per land instance (`LandLifecycleRecord`). The events:
  - `created`, when the instance is published;
  - `removed`, when it is removed by ID, for example by the admin API's delete. The instance keeps its players and is destroyed later.
  - `destroyed`, when its destruction ends, with `cause` `emptyTimeout`, `forceShutdown` or `initializationFailed`.

  Each line carries the land ID and type, a process-monotonic `instance` number, the manager's `epoch`, `wallMs` (ms since 1970, the profile's `ts` base) and `uptimeNs` (`ProcessInfo.systemUptime`, monotonic). A land recreated under the same ID gets a new `instance`. The log bypasses the logger's level filter, so it works with `LOG_LEVEL=error`, and it costs one write per event, nothing per tick or sync. The file is opened with `O_APPEND`, so processes may share it; each numbers its instances from 1. A path that can't be opened, or a failed write (a full disk), disables the log with one error line; the server keeps running.

  The same file also gets two session lines (`SessionLifecycleRecord`):
  - `sessionJoined`, which the land's adapter writes when a join completes. It carries the `sessionID`, the `playerID`, the `landID` and the land's `instance`.
  - `sessionClosed`, which the NIO session handler writes when it decides the close. It carries the `sessionID`, a `cause` and the close `code` when there is one.

  The causes:
  - `pongTimeout` (1001);
  - `backlogBytes` and `backlogUnwritable` (4008);
  - `clientClose`, with the client's code;
  - `serverClose`, a close the transport requested, with its code: a join error, a kick or a shutdown, not told apart. A graceful server shutdown (`NIOLandHost.shutdown()`, `runUntilShutdownSignal()`) closes every session it still holds with 1001 Going Away, so it logs `serverClose` with 1001, the same code as a pong timeout but with its own cause;
  - `connectionLost`, when the channel went away (an EOF, or a failure with a reset, a broken pipe or a timeout) with no close decided before;
  - `error`, when the server closed on another error, such as a protocol error.

  A session gets exactly one `sessionClosed`, for the first cause decided.
  - **Pairing:** the two lines pair by `sessionID`, in either order. NIO hosting makes it unique per connection, with one UUID per WebSocket upgrade. A close is decided on the connection's event loop, while a join read before it can still complete in its land afterwards, so a `sessionClosed` line may come before its `sessionJoined`. A session can join more than once; its close applies to every join with its `sessionID`.
  - **Instance numbers** are drawn when a land is built, and `created` is written when it is published. So `created` lines aren't in `instance` order, and a build that is never published (torn down first) leaves a gap.
  - **Where to put the file:** on a local disk. Every line is written synchronously from the manager, the adapter or the event loop, so a slow network file system would slow those down.

Boolean parsing: truthy = `1`, `true`, `yes`, `y`, `on`; falsy = `0`, `false`, `no`, `n`, `off`.

## Profiling

With `TRANSPORT_PROFILE_JSONL_PATH` set, the adapter writes one JSON line per interval. Besides message counts and latency samples (`decode_ms`, `handle_ms`, `encode_ms`, `send_ms`), each line counts the sync cycles of that window:

| Counter | Meaning |
|---|---|
| `syncCycles` | sync cycles that committed their plan (both paths): the denominator for the others |
| `syncSkipsBacklog` | cycles skipped for writer back-pressure |
| `syncDeferredTurns` | of `syncSkipsBacklog`: in-turn sync phases deferred by back-pressure |
| `syncSkipsBusy` | requests rejected because another cycle was in flight (legacy path) |
| `syncFolds` | in-turn sync cycles folded into the next tick turn (coincident sync), at most one per cycle |
| `syncOverdueFolds` | of `syncFolds`: folds whose tick was already overdue, so the frame waited for a late tick |
| `syncFailedPlans` | sync plans that threw and committed nothing |
| `syncDroppedUpdates` | patches, updates or fields dropped because they did not encode or extract |

Sync phase times: `sync_extract_ms`, `sync_broadcast_ms` and `sync_perplayer_ms`, each `{sum, plans, mean}` over the window's full sync plans. They cover snapshot extraction, the broadcast diff and the per-player diffs. Extraction yields the broadcast and per-player snapshots in one call, so it isn't split between them. Encoding, frame planning and the full views of joiners are in none of the three. The broadcast share of the diff work is `sync_broadcast_ms / (sync_broadcast_ms + sync_perplayer_ms)`. `sync_combined_plans` counts the plans without merged broadcast frames: their per-player time includes folding the broadcast diff into each player's update, so filter on it or state the mode. The clock is read only while profiling is on.

Each line also has `pongTimeoutCloses`: WebSocket sessions closed because no frame arrived within `WS_PONG_TIMEOUT_MS` after a keepalive ping (NIO hosting). It also has `closeFrameTimeouts`: server closes whose close frame wasn't written within 5 s, so the channel was closed without it. That happens with a client that stopped reading while its channel was still writable (NIO hosting).

At a graceful shutdown (`NIOLandHost.runUntilShutdownSignal()`) the profiler writes one last line with the counters since the previous one, marked `"final": true` with its real length in `interval_ms`. It is shorter than a full window, so leave it out of per-window counts and maxima. ws-loadtest's readers skip it entirely: their totals leave out that last partial window and are a lower bound for the whole run, so compare them only with totals read the same way.

Deadlines (#104): `resolverTimeouts` and `resolverInitTimeouts`, resolver groups past `RESOLVER_TIMEOUT_MS` or `RESOLVER_INIT_TIMEOUT_MS`; `resolverInitFailures`, OnInitialize resolver groups that threw and failed their land's initialization (`.failLand`, #238); `onLeaveDropped`, OnLeave inputs dropped because their resolvers failed or timed out; and the joins out of budget by phase, `joinTimeoutsLandLookup`, `joinTimeoutsAdmission` and `joinTimeoutsFlip`. Each counts the interval. `abandonedResolvers` is a gauge: resolver groups whose caller stopped waiting, at the deadline or on cancellation, that are still running. A resolver that never ends keeps it up. `abandonedActions` is the same gauge for actions only, and `actionInFlightLimitRejections` and `actionAbandonedLimitRejections` count the actions the two caps rejected in the interval.

Send backlog (NIO hosting, #61), measured; the [bound](#send-backlog-bound) closes a session over it:
- `sendBufferedBytesMax`: per window, the largest number of bytes any session's channel buffered while unwritable (NIO's `bufferedWritableBytes`, written but not yet accepted by the socket). It is sampled only above the write high watermark (default 64 KiB), when the channel turns unwritable and after each write while it stays so; 0 means no channel went above it.
- `sendUnwritableEpisodes`: sessions whose channel went above its write high watermark in the window.
- `sendUnwritableLongestMs`: the longest of those episodes that ended in the window.
- `sendUnwritableSessions`: a gauge, not reset per window: sessions unwritable when the line was written. It is a sample at each window's end, not the peak: a session that goes unwritable and recovers within a window shows only in `sendUnwritableEpisodes`.

- `sendBacklogCloses`: sessions closed by the send backlog bound in the window.

Inbound backlog (NIO hosting, #113); the [bound](#inbound-backlog-bound) stops reading a session over it:
- `inboundQueuedMessagesMax`, `inboundQueuedBytesMax`: per window, the most messages (bytes) any session had read but not yet delivered to the transport.
- `inboundReadPauses`: times a session stopped being read at the bound in the window.
- `inboundPausedLongestMs`: the longest of those pauses that ended in the window.
- `inboundPausedSessions`: a gauge, not reset per window: sessions not being read when the line was written.

ws-loadtest reports them per phase as "Server send backlog".

### Send backlog bound

A session whose client does not drain is closed (#61, option A), like Redis's hard `client-output-buffer-limit`. Either bound closes it:
- **bytes:** its channel buffers more than `WS_SEND_BACKLOG_MAX_BYTES` while unwritable. It is checked where the backlog is sampled (above the write high watermark, 64 KiB by default), so a bound below the high watermark acts only once the channel is above it. A single frame larger than the bound closes even a client that drains normally, so keep the bound well above the largest frame (a firstSync of a large state, for example);
- **time:** its channel stays unwritable longer than `WS_SEND_BACKLOG_MAX_UNWRITABLE_MS`, timed from when it became unwritable. Turning writable again, or the session ending, cancels the timer.

The server sends a close frame with code **4008** and closes the connection at once, without waiting for that frame to be written. A server close already under way (a supersede, an admin close) doesn't stop the bound: its close frame may wait behind the same backlog, so the bound closes the connection anyway. The frame queues behind the backlog the server is reacting to, so a client that isn't draining usually sees the connection drop (1006 in a browser) rather than 4008. The server's record is reliable: `sendBacklogCloses` in the profile, and a warning log line with the session, the bound and the value that broke it.

A client rebuilds by reconnecting and joining again: the new view starts empty and its firstSync is the player's complete view (see the SDK's [delivery semantics](../sdk/README.md#delivery-semantics-at-most-once)). Pending actions are rejected, with an unknown outcome.

A backed-up client that sends nothing can also hit the pong timeout (`WS_PONG_TIMEOUT_MS`, 20 s) before the 30 s time bound, because the keepalive ping queues behind the backlog. Either closes it; `pongTimeoutCloses` and `sendBacklogCloses` tell the two apart.

### Sync lag and in-place resync

Every hosted land tracks sync lag: the server tracks how far each client is behind the state it was sent, from the client's own acks (#332). The send backlog bound is a last resort for a client that stops draining. This one acts earlier, while the client is still connected, and without a reconnect.

- **The sequence.** Every sync plan takes the land's next sync sequence, and every state-update frame of that plan carries it: `[op, seq, patch…]` in the opcode encodings (opcode 107's state array the same), and a `seq` key in the JSON object encoding. A plan that doesn't commit leaves a gap. The sequence adds 1–9 bytes to every state frame in the opcode encodings.
- **The handshake, and a compatibility break.** Every hosted land requires `syncSequence` in the join's `stateUpdateFeatures`, the same way as `pathIndex`. A client that doesn't declare it, an SDK or load client older than this change, is refused at join. There is no opt-out yet; one can be added later.
- **The ack.** The client sends `[108, seq]`, the last sequence it applied, in its message encoding. The SDK sends one every second (`ackIntervalMs`), one from the apply path once that interval has passed (a hidden tab throttles timers), and one at once after a firstSync or a resync. An ack isn't a transport message: the router hands it to the land's adapter, and the land never sees it. Every ack counts as a sign of life, an unchanged value included.
- **Lag** is the age of the oldest frame committed to the session that it hasn't acked yet.
- **The decisions**, made by each sync plan for its recipients, and by a 250 ms timer for closes and for lands without periodic sync:

| Condition (checked in this order) | Decision |
|---|---|
| Its oldest unacked frame is a full view (a firstSync or a resync), unacked for `SYNC_ACK_TIMEOUT_MS` (10 s), while acks still arrive | Close with **4010** (slow consumer) |
| Frames are unacked, and no ack arrived for `SYNC_ACK_TIMEOUT_MS` | Close with **4011** (unresponsive) |
| Its oldest unacked frame is a full view | Nothing: a full view is exempt from the lag rule |
| Lag over `SYNC_LAG_RESYNC_MS` (3 s), and no ack within `SYNC_ACK_FRESHNESS_MS` (2 s) | **Pending:** no more frames for it, its events dropped, until acks resume |
| Pending and acks arrive again, or lag over `SYNC_LAG_RESYNC_MS` with fresh acks | **In-place resync**, or 4010 when it would be the `SYNC_LAG_SLOW_CONSUMER_COUNT`th (3rd) within `SYNC_LAG_SLOW_CONSUMER_WINDOW_MS` (60 s) |

- **The in-place resync.** One sync plan gives the session the player's whole view on its live connection, typed **resync** (opcode 3, or `"type":"resync"`). A client decodes it as a firstSync. Every client must handle opcode 3 (state-update opcodes are now 0–3): a client that ignores it keeps a stale view, and a Swift `switch` over `StateUpdateOpcode` or a TS one over the opcode union needs the new case. With merged frames (opcode 107), the session gets the snapshot first and then the merged broadcast frame with the same sequence, which can carry the broadcast key scope's reset. A client reads that frame's key definitions and events and skips its state patches, which the snapshot already holds; the SDK, ws-loadtest and the CLI do, and the ack of that sequence follows the snapshot. The land sees nothing: no leave, no join, and the player's state stays as it is. Every session of the player gets the snapshot, since the view is per player, but only the lagging session's count grows. The events of that plan's own cycle go out with it, as for any recipient; only the events consumed while a session is pending are dropped and counted. A resync makes the next merged broadcast frame reset the broadcast key scope for every client in the land, as a rejoin does; several resyncs in one plan share one reset. A recorded sync stream gets a clear and then a seed marked as a rejoin, as a reconnect does, so replay verification checks the new view.
- **A snapshot that doesn't encode whole** (a value the encoding can't carry, such as a NaN in JSON) isn't sent: a resync replaces the client's view, so a snapshot missing a patch would delete that field on the client. The session stays as it was, and the next plan tries again. After 3 failed snapshots in a row the session is closed with **4012** (unencodable view); the count resets when the session no longer needs a resync: one goes out, or it catches up by its acks (its lag back under `SYNC_LAG_RESYNC_MS`).
- **Closes.** 4010, 4011 and 4012 end the connection; no client rejoins on its own. The SDK reports the code through `onDisconnect`. ws-loadtest reopens the connection only with `--reconnect on-server-close`, as for any server close. ServerLoadTest counts the closes in `serverClosesByCode`.
- **The close grace** (#339). Once the close frame of a 4010, 4011 or 4012 close is written, the server keeps the connection open for up to `SYNC_LAG_CLOSE_GRACE_MS` (2 s). During that time it reads the socket, past an inbound pause, and discards everything it reads. It closes the channel when the client's close frame arrives or the grace runs out. Closing at once with unread inbound data (the acks a lagging client sent before it saw the close) makes the kernel send an RST, which can discard the close frame on the client's side: the client would see 1006 instead of the code. Writing the close frame stays bounded by the close-frame timeout (5 s). A `SessionClose` carries its grace in `closeGrace`. A server shutdown's 1001 closes have a 500 ms grace, which the shutdown waits for within its sessions step; other server closes have none. Nothing read in the grace is kept: each frame is bounded by the maximum frame size and dropped, so the cost is the grace's length of reading. `WebSocketTransport` waits that much longer for the closed connection's callback (`serverCloseConfirmDeadline(for:)`, the 10 s confirm timeout plus the grace), so a long grace never makes the transport forget the session while its channel is still open.
- **The SDK** reconciles a resync with the view it has. It builds the new state, diffs it against the old one, and notifies only net changes: `onPatch` per change, then `onStateUpdate` once, then the map subscriptions (net adds and removes), then `onResync`. Unchanged subtrees keep their object identity, so references a game holds stay live.
- **Counters** (adapter): `syncLagResyncs`, `syncLagResyncsAlongside`, `syncLagPendingMarks`, `syncLagKeyScopeResets` and `syncLagKeyScopeResetBytes` (the reset frame's bytes over its recipients), `syncLagDroppedEvents`, `syncLagSlowConsumerCloses`, `syncLagUnresponsiveCloses`, `syncLagDroppedAcks`, `syncLagSnapshotEncodeFailures` (snapshots not sent) and `syncLagUnencodableCloses`. The transport profile (`TRANSPORT_PROFILE_JSONL_PATH`) carries the same counts per window, summed over the land's adapters: `syncLagResyncs`, `syncLagResyncsAlongside` (the player's other sessions that got the snapshot), `syncLagPendingMarks`, `syncLagKeyScopeResets`, `syncLagKeyScopeResetBytes`, `syncLagDroppedEvents`, `syncLagSlowConsumerCloses` (4010), `syncLagUnresponsiveCloses` (4011), `syncLagDroppedAcks`, `syncLagSnapshotEncodeFailures` and `syncLagUnencodableCloses` (4012). ws-loadtest acks and counts the resyncs each connection gets. ServerLoadTest's in-process clients ack once a second and report the acks sent and any server closes by code (`totalSyncAcksSent`, `serverClosesByCode`).
- **Configuration.** `NIOLandServerConfiguration.syncLag` is a `SyncLagPolicy` with every threshold above. Its default is `SyncLagPolicy.fromEnvironment()`, and a value set in code replaces it. Tracking runs on hosted lands only: a `TransportAdapter` or `LandManager` built through its public initializer sends no sequence and tracks nothing.
- **A close** is decided in one synchronous step with the connection's generation, so it never closes a later connection that reuses the session ID.

### Inbound backlog bound

A session's messages reach the transport one after another, each after the previous one's handling returned (the per-session inbound chain). While one is slow, the ones behind it wait: during a join's land lookup, for example. The server keeps reading the socket meanwhile, so a client that keeps sending would pile messages up in memory. The bound stops that (#113):
- **over the bound:** with more than `WS_INBOUND_BACKLOG_MAX_MESSAGES` messages, or more than `WS_INBOUND_BACKLOG_MAX_BYTES` bytes, read but not yet delivered, the server stops reading the session's socket. TCP flow control then slows the client down. Nothing is closed and nothing is dropped.
- **resume:** reading resumes once both are at or below half their bound. Messages keep their order across a pause.

The bound is a soft limit on the payload backlog of one session. It can be exceeded by what was already read when it was crossed. That is every frame decoded from the same read cycle: up to 16 socket reads of up to 64 KiB each (1 MiB) with this server's channel settings. On top of that comes one message still being reassembled, up to the server's maximum frame size. The decoder's buffers and per-message overhead come on top of the payload. The bound is per session; nothing here bounds the sum over sessions.

A paused session reads no frames, and that includes its client's close frame and keepalive pongs. A client's own close is therefore seen only when reading resumes. A keepalive ping sent during the pause goes unanswered. If the pause outlasts that ping by `WS_PONG_TIMEOUT_MS`, the session is closed with 1001, as an unresponsive client would be (`pongTimeoutCloses`). Pings go out every 30 s, so a pause can last up to about 50 s before that. That is the interim bound on a stuck operation. Server-side closes act while paused, as do the close-frame timeout and the send backlog bound.

Once a join is admitted on the in-turn path, its frames go to the land's adapter, which holds them until the join completes, up to its own bound (256 frames or 256 KiB, `JOIN_INBOUND_OVERFLOW`). That bound trips first. The inbound backlog bound acts while the router's handling of a frame is itself suspended: before the admission, or in an action dispatch held by a slow resolver.
