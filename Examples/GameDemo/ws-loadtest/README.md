# WS Load Test (Hero Defense)

This tool runs a **real WebSocket client** load test for the `hero-defense` land using Node.js `ws` clients.
It supports multi-process workers, phased scenarios, and generates **JSON + HTML** reports.

## Quick Start

```bash
cd Examples/GameDemo/ws-loadtest
bash scripts/ensure-deps.sh
npm run build
bash scripts/run-ws-loadtest.sh --scenario scenarios/hero-defense/default.json
```

ws-loadtest depends on the TypeScript SDK through `file:../../../sdk/ts` and imports its built `dist/`, so on a fresh checkout `npm run build` here fails (TS2307 on `@swiftstatetree/sdk/...`) until `sdk/ts` is installed and built. `scripts/ensure-deps.sh` does that: `npm ci` in `sdk/ts` when its `node_modules` is missing or older than its lockfile, `npm run build` there when `dist/` is missing or older than its sources, then `npm ci` here on the same rule. It uses `npm ci` only, so neither `package-lock.json` is rewritten, and does nothing when all are current. `run-ws-loadtest.sh` (and so `run-scalability-test.sh`) runs it and this package's build before starting the server.

Reports are written to:
```
Examples/GameDemo/ws-loadtest/results/
```

## External server

`bash scripts/run-ws-loadtest.sh --external-server <pid> [--external-profile <file>] ...` runs the client against a GameServer the caller started and owns, for example one in another network namespace. The script doesn't build, start or stop a server, and doesn't check port 8080. Instead it checks that the scenario's `serverUrl` accepts a TCP connection, and fails if the PID isn't running. The system metrics sample that PID. `--external-profile` names the transport profile JSONL that server writes, which the caller enables by starting it with `TRANSPORT_PROFILE_JSONL_PATH`; `--profile` is refused in this mode, since it starts the server. `toolchain.txt` records the PID, its binary when `/proc` shows it, and `GAMESERVER_SOURCE_SHA`. The reevaluation-records check is skipped, since that directory is the caller's.

## Network impairment (Linux)

`scripts/impair.sh` builds the topology of the network impairment design (`Notes/plans/2026-11-07-network-impairment-experiment-design.md`, § 1), and applies and lifts its profiles. It needs root, iproute2, ethtool and the `sch_netem`, `sch_prio` and `cls_u32` modules. The load client runs in namespace `lt-client` (and `lt-good` for mixed populations, `setup --with-good`); `lt-router` forwards and shapes; the server listens on 10.200.0.1 in the caller's namespace.

- `setup --limit-down N --limit-up N [--fifo-limit N] [--with-good]`: namespaces, veths with TSO, GSO and GRO off, routes, and the qdisc trees. The netem limits are required: the default of 1000 packets overflows at load.
- `apply <profile> [--rate <tc rate>]`, `lift`, `schedule <profile> --at <epoch ms> --for <s>`, each with `--timeline <file>`: in-place `tc qdisc change` on both directions. Every change states every netem parameter (delay, jitter, loss, rate as `0bit` when none, and the setup's limit): `tc qdisc change ... netem` resets the base parameters it isn't given (`limit` to 1000) but keeps an optional one such as `rate`. After each change, `scripts/netem-check.mjs` compares the `tc -s qdisc` after-snapshot with the profile; a mismatch fails the command once its timeline entry is written. `RATE` and `COMBO` take `--rate`, their fraction of P0's measured downstream. `COMBO_NORATE` is COMBO's delay, jitter and loss without the rate; it calibrates COMBO's delay (design § 1) and isn't a sweep profile. The timeline is a JSON array with each change's commands, wall-clock and monotonic times, and `tc -s` and `ethtool -k` output before and after. A lift's `ss -tin` capture of every impaired socket goes to a side file, `<timeline>-sockets-at-lift-<n>.txt`, which the entry names (`socketsAtLiftFile`) with its size and the capture's start and end times. A change whose entry can't be written fails loudly, saying when the change ran.
- `sample-backlog --out <file.jsonl>`: each netem's and pfifo's backlog, sent and dropped counters, once per second until stopped.
- `show`, `teardown`, `profiles`. `IMPAIR_DRY_RUN=1` prints the commands instead of running them.

**Convergence** (design § 6). `--reconstruct` gives every connection a client state, rebuilt by the TypeScript SDK's `StateTreeView` from the frames it receives: the SDK's `decodeMessage` with the connection's own dynamic key maps, routed as `StateTreeRuntime` routes them. The schema comes from the server's `/schema`, fetched once before the workers start. The tool's own decode stays as it is for the metrics, so each frame is decoded twice. `npm run build` bundles the SDK's core into `dist/sdk-core.cjs` (`scripts/bundle-sdk.mjs`), since Node can't resolve the core index's extensionless imports. `tests/reconstruction.test.ts` feeds recorded GameServer frames (`tests/fixtures/hero-defense-frames-<encoding>.json.gz`, from `scripts/record-frames.mjs`, one per `TRANSPORT_ENCODING`) to the SDK's own client, to the reconstruction and to the tool's decoder, and checks they agree on the state, the frame classes and the decode errors. Two changes it doesn't catch are equivalent for the state only under this tool's setup: dropping the events of an opcode-107 frame (no event handlers are registered, and events don't change the state), and ignoring the join response's decoding switch (the decoding stays `auto`, which tries both state-update formats).

**Row addressing** (`rowAddressing`, #392). A join declares it only with `--row-addressing on` (default off). The declaration is join metadata, which a recording server (`ENABLE_REEVALUATION=true`) keeps in its records, so a run without the flag sends byte for byte the join it sent before the client decoded row entries. A server negotiates the feature only with `ROW_ADDRESSING=true`, and refuses a join without it there, so a run against such a server needs the flag. The plan is to make the flag default on once row addressing is the server default (#392); until then it stays off. The run summary records the flag (`meta.runConfig.rowAddressing`) and, per phase, each join's negotiated features (`stateUpdateFeatures`), the row entries the clients received (`rowEntries`) and the 4013 closes (`rowEntryCloses`): a run with row addressing in effect shows `rowAddressing` in its join keys and `rowEntries` above 0. **The strict rules are checked in full only with `--reconstruct`.** There, the SDK's decoder reads every row entry, and a broken rule closes the connection with 4013 as the SDK does (close cause `rowEntry`, with its rule; no reconnect). Without `--reconstruct`, the tool's own decoder only counts row entries and checks one rule, a row entry without the feature negotiated, which closes the same way. A run without `--reconstruct` is therefore not a strict check of the row entries.

`--control-socket <path>` (needs `--reconstruct`; at most 103 bytes, a Unix socket limit) serves the instance's control channel, HTTP on a Unix socket: `POST /stop-sending` ends every worker's action and event sends and keeps the connections open; `GET /lands[?land=<id>][&states=<id>]` reports each connection's land, player, server player, whether it is open, whether its session came from a reconnect, its decode errors and the time of its last frame (any frame, decoded or not), and, for the lands in `states`, its normalised state. `node dist/converge-main.js --control <name>=<socket> ... --admin-url <url> --api-key <key> --deadline-s <s> --out <file>` is the driver (`src/converge.ts`): it stops the sends, then runs the `Tools/CLI` check (#79) per land, at most 20 at once (`--concurrency`, refused above 20): freeze through the admin debug routes (the server needs `ENABLE_DEBUG_STATE_ROUTES=true`), wait until no connection of the land received a frame for 200 ms (3 s at most), compare each open connection's state with its player's projection (`compareStates` from the SDK, the CLI's comparison), and resume. The quiet window doesn't prove the last frame arrived (a tail loss waits for a TCP retransmit), so a connection that differs is read again every 100 ms against the same projection until it matches, "converged late" with its delay, or 5 s after the freeze, a mismatch; after the re-reads one projection is fetched again, so a membership change while frozen makes the land inconclusive. A resume that fails is retried once; a second failure makes the land an error. A land whose membership changed is retried once. A connection that isn't open is a missing client. `--deadline-s` (required, so a manual run can't overrun the scenario's tail) starts no land check later than that after the start; the lands left are errors, counted as `uncheckedAtDeadline`. The report lists every land and the roster (connections per land per instance, as the instances listed them), and counts survivors and reconnected connections apart.

## Scalability test (multiple runs)

Run the same scenario multiple times and aggregate pass/fail and metrics (similar to `Examples/GameDemo/scripts/server-loadtest/run-scalability-test.sh`):

```bash
cd Examples/GameDemo/ws-loadtest
bash scripts/run-scalability-test.sh --no-scale-by-rooms --runs 5 --scenario scenarios/hero-defense/default.json
```

Notes:
- Default mode is **scale-by-rooms** (100 → 300 → 500 → 700). Run it with: `bash scripts/run-scalability-test.sh --scale-by-rooms` (or simply `bash scripts/run-scalability-test.sh`).
- To run the same scenario N times, use: `bash scripts/run-scalability-test.sh --no-scale-by-rooms --runs <N>`. With a room list (`--room-counts`, or scaling by rooms) each room count is one run, and `--runs` is an error; to repeat a room list, run the script again.
- To control client-side worker processes, use: `--workers <N>` (default: CPU cores).
- `run-scalability-test.sh` passes the client options to every run's `run-ws-loadtest.sh` as given: `--layout`, `--connect`, `--connect-rate`, `--boundary`, `--send`, `--window-ms`, `--warmup-seconds`, `--allow-partial-ramp`, `--allow-join-failures`, `--input-latency`, `--move-to-rate` and `--event-seed` (see Layout, Moving players and Metrics → inputToVisible). `--run-id` isn't forwarded: each run gets its own.
- To run a GameServer built elsewhere (another commit) against this client, set `GAMESERVER_BIN=<path to the GameServer binary>`, and `GAMESERVER_SOURCE_SHA=<its commit>`. The script then skips building this checkout's server, starts that binary, and adds both values to each run's `toolchain.txt`. Unset, it builds and runs this checkout's GameServer.

Options: `--runs <N>`, `--no-scale-by-rooms`, `--room-counts "N1 N2 N3"` (scale by room count), `--workers <N>`, `--scenario <path>` (relative to ws-loadtest/ unless absolute, in both scripts), `--output-dir <dir>`, `--startup-timeout <s>`, `--delay <s>` (seconds between runs), `--profile` (enable transport profiling). Output is written to `results/scalability-<timestamp>/` with a `summary.json`, per-run logs/reports, and a **summary.html**. The summary report is generated as a **static HTML** (no runtime Vue/JS required): the template is `scripts/scalability_summary_template.html` and `scripts/render-summary-html.js` renders `summary.json` into the final HTML, so you can edit the template and re-run the script to change the report layout.

## CLI

`node dist/cli.js --help` prints every option. An unknown argument exits non-zero with the usage and starts no run; before 2026-11-06 unknown arguments, `--help` included, were ignored and ran the default scenario.

```bash
node dist/cli.js \
  --scenario scenarios/hero-defense/default.json \
  --workers 4 \
  --output-dir results \
  --system-metrics monitoring/system-metrics.json \
  --transport-profile results/transport-profile.jsonl
```

Add `--input-latency on` to time move events until visible (`inputToVisible` under Metrics).

`--transport-profile` reads the server's transport profile (JSONL, one window per line, written when the server runs with `TRANSPORT_PROFILE_JSONL_PATH`; `run-ws-loadtest.sh --profile` sets it and passes the file). The report's `serverSync` block then gives, per phase, the server-wide sync counters over that phase's measured window, the same span as the client metrics (warm-up excluded). Only profile windows wholly inside the measured window count, so the covered span (stated per phase) can be up to one window shorter at each end; the CLI waits for the window that closes the last measured window to be flushed before reading. The counters: committed sync cycles; skips for writer backlog, of which in-turn deferrals; skips for a cycle in flight; sync cycles folded into a tick turn, of which past the tick's deadline when the sync loop ran (mostly a loop race, see METRICS.md). A fold counts once per cycle. The block leads with folds per 1000 sync cycles and late folds per 1000 sync cycles, the share of cycles whose tick turn started more than the coincident-sync window late (#232), with the largest fold lateness next to its threshold; those two read n/a for a server before #232. For each counter the block gives the total and the max in one window, plus the windows with a past-deadline fold. The windows are placed by the server's wall clock and the measured window by the client's, so with the server on another host, clock skew between the two shifts which profile windows count; keep both hosts NTP-synced, or treat the covered span's ends as uncertain by the skew. Without a profile, or with one from a server older than these counters, the block is `null` and the HTML says "n/a"; a phase with no profile window inside its measured window says "n/a" too.

## Room layout and connections

- **Layout** (`--layout`, default `rooms`): a phase's `rooms × playersPerRoom` connections join `rooms` lands of `playersPerRoom` players (`<runId>-room-p<playersPerRoom>-<room>`). Whole rooms go to one worker. `--layout per-connection` is the earlier behaviour: one land per connection (`<runId>-<phase>-<worker>-<i>`).
- **Run id**: every land id starts with a new short id per run (`--run-id` to set it), so back-to-back runs on one server never join each other's live or draining lands. `run-scalability-test.sh` restarts the server for every run anyway; the id matters when the CLI runs against a long-lived server.
- **Shared rooms** (`--room-slots`, `--start-at`): two client instances can fill the same rooms, for example one in an impaired network namespace and one in a healthy one. Both pass the same `--run-id`, so they generate the same land ids, and each passes its own slots: `--room-slots 0-149:0` holds slot 0 of rooms 0–149, and `--room-slots 0-149:1-4,150-299:0-4` holds the rest. Ranges are inclusive. A (room, slot) named twice, or a room or slot outside any phase's `rooms` / `playersPerRoom`, is refused rather than skipped. `--start-at <epoch ms>` starts the first phase at that time, after the workers are up, so both instances begin together; a time already past is refused. A phase's `target` is then this instance's planned connections, and `meta.runConfig` records `roomSlots`, `startAt` and `firstPhaseStartedAt`. `run-ws-loadtest.sh` forwards both options, and adds the wait until `--start-at` to its timeout. `run-scalability-test.sh` refuses them, since its runs restart the server and use their own run ids.
- **Stale check** (`--stale-after <s>`, e.g. `10s`): a joined connection that has had no frame from the server for that long is abandoned by the client: terminated, and recorded as a client-initiated close with `cause: "stale"` and `silentForMs`. It counts as a disconnect, and the close summary's `stale` counts them. Every worker checks its connections every 250 ms, so detection lags the threshold by at most that. A stale connection isn't kept, so the next phase opens it again. Off by default.
- **Slow reader** (`--slow-read <start>:<duration>`, seconds): every connection of this instance stops reading its socket (`pause()` on the TCP socket) for `<duration>`, starting `<start>` after the first phase starts, and keeps sending on schedule, so the server's send buffer for it fills. A connection that joins inside the window pauses at once, until the window ends. The stale check is suspended while reading is paused, and its timer restarts at the resume. A client close resumes reading first, so its handshake can finish. The connection's close record carries `slowReader`, `readPausedAt` and `readResumedAt`, and `meta.runConfig.slowReadWindow` the window in ms since epoch. To make only some players slow readers, run them as a second instance with `--room-slots`.
- **Reconnect** (`--reconnect on-server-close`, `--reconnect-until <s>`): a joined connection closed by the server or by the stale check is reopened: 1 s later, one connect and join with a 5 s timeout, and after a failed attempt the next one 1 s later, never two at once. No attempt starts later than `--reconnect-until` seconds after the first phase starts (default: until the run ends). It is a new join to the same land with the same connection key, not a resumption: the server assigns the player again. Failed attempts leave no close record and no join failure. Each reconnect ends as `recovered` (joined, then a firstSync), `joinedNoFirstSync`, `gaveUp` or `cancelled` (the tool closed it), and is reported in the phase's `connectionLifecycle.reconnects` with its close cause, attempts, `downtimeMs` (close → firstSync), `connectMs` and `joinToFirstSyncMs`, and in the raw samples. A connection still reconnecting at a phase boundary isn't kept: the next phase closes it and opens a new one.
- **Raw samples** (`--samples-dir <dir>`): each worker writes every event, as it happens, to `<dir>/w<worker>.ndjson.gz`: one JSON record per line, gzip-compressed, flushed at shutdown. The records are phase starts, joins, every action (intended and actual send time, and the response time, or why there was none: its phase ended, or its connection had closed), the first answer to a request a phase end left unanswered (`late`, with its outcome), every state update (arrival, gap, bytes), every move event with `--input-latency on` (seen, superseded, timed out, or pending when its connection closed), and every close with its player. They hold raw times, not classifications, so a later analysis can segment them by any timeline. The format is documented in `src/samples-sink.ts`, and `readSamples` reads a file back. `meta.runConfig` records the directory and the file names. At hundreds of rooms this is hundreds of MB per run, so it is off by default.
- **Connect** (`--connect`, default `ramp`): new connections open at about `--connect-rate` per second over all workers (default 1000/s), each jittered inside its slot. `--connect burst` opens them all at once (join-storm tests). A phase whose ramp needs longer than the phase fails the run before it starts. `--allow-partial-ramp` runs it anyway with a warning, and the phase's `connectionLifecycle` then shows `started` and `joinedAtEnd` below `target`.
- **Across phases** (`--boundary`, default `clean`): workers live for the whole run. A connection whose room is also in the next phase stays open; the others are closed with a close frame (code 1000) before the next phase opens new ones. At the end every connection is closed the same way. With the `rooms` layout, phases with the same `playersPerRoom` share lands and connections. `--boundary abrupt` drops those sockets without a close frame instead (the server sees FIN or RST, depending on unread data).
- **Legacy topology**: `--layout per-connection --connect burst` gives the same topology and connect burst as the old tool. Phase boundaries still close cleanly, unlike the old tool's resets, so the boundary load and the first seconds of each phase differ. Add `--boundary abrupt` to drop the sockets at boundaries as the old tool did. The sockets are then dropped when the next phase starts rather than as each worker exits.
- **Report**: `meta.runConfig` records the run id, layout, connect mode and rate, boundary mode, workers, and every phase's rooms, players, connections, lands and ramp time. Each phase has `layout` (lands, players per land) and `connectionLifecycle`: target, started, joined at the end, opened, reused, closed at start, ramp duration, and close counts split by initiator and code, plus the first 200 close records. `disconnectRate` counts only closes the client didn't ask for, including server closes on connections between phases. `meta.shutdownCloses` covers the end of the run.

## Sending and measurement

- **Phase start**: a phase starts in two steps. Every worker first closes the previous phase's surplus connections and gets ready, and only then is the common origin taken. Connects (the ramp) and sends count from that origin. Each phase's `connections.transitionMs` is how long the transition took.
- **Send schedule** (`--send`, default `spread`): each client sends at `origin + offset + n · period` (`period = 1000 / actionsPerSecond` ms). The per-client offset in `[0, period)` comes from a stable hash of the connection, so a land's actions are spread over the tick and sync phase and runs are reproducible. A timer that fires late sends every slot it missed. `--send lockstep` is the earlier behaviour: one timer per worker sends for all of its joined clients at once.
- **RTT origin**: in `spread` mode RTT is measured from the intended send time, so client-side queueing and stalls show up as larger RTT, not as missing samples (no coordinated omission). The report also gives the send lag (actual minus intended), the late sends (more than one period late) and the achieved send rate against the target. The target is the rate × the time-weighted average of joined, open clients over the measured window. In `lockstep` mode RTT is measured from the actual send, as before.
- **Warm-up**: RTT and update samples, errors, server disconnects and sends in the first `warmupSeconds` of each phase are excluded from the phase's `report` and thresholds. `phaseTotals` keeps the whole-phase error, disconnect and send counts, transition included. Set it per phase in the scenario or for all phases with `--warmup-seconds`. The default is the phase's connect ramp + 2 s, at most half the phase. Each phase's `measurement` block gives the resolved warm-up and the excluded sample counts.
- **Joins**: a join fails when the server rejects it (`error`: an error frame, e.g. a full room; `rejected`: a join response with `success: false`), the connection closes before it joined (`closed`), or nothing answers it within 5 s of connecting, or by the phase end if sooner (`timeout`; a late answer doesn't join). Each phase's `connectionLifecycle.joinFailures` counts them over the phase and in the measured window, by reason, and `joinFailureRecords` lists the first ones. The HTML report has a join-failures column and lists each FAIL row's reasons. Join failures are not counted in `errorCount`. A phase **fails**, whatever the scenario's thresholds are, when any join failed, when fewer than `target` connections are joined at the phase end (`measurement.joined.atEnd`), or, when the warm-up is longer than the connect ramp (the default), at the measured-window start (`joined.atMeasuredStart`, which catches joins slow enough to leave part of the window unloaded). With a shorter warm-up (e.g. `--warmup-seconds 0`, or a burst connect without warm-up) that check is skipped and `atMeasuredStartNote` says so. The window-start check needs a margin: a warm-up only slightly longer than the ramp fails it when the ramp overruns or a join's round trip lands after the window start. The default warm-up (ramp + 2 s, at most half the phase) is the safe margin; when setting `--warmup-seconds` yourself, keep at least that much above the ramp, or set it to 0 to skip the check. The time-weighted `joined.average` over the window is reported only. Only joined connections are kept for the next phase: one that didn't join is closed at the transition, and the next phase opens a new connection that joins again. `--allow-join-failures` turns both checks off. With `--allow-partial-ramp` the joined counts are compared with the connections the phase held (kept or started by the ramp) instead of `target`. The resolved flags are in `meta.runConfig`.
- **Update samples**: state updates are recognized in every encoding: jsonObject `{ type: noChange | firstSync | diff }` frames and the opcode arrays (opcodeJsonArray, messagepack, and the merged 107 frame). A phase whose joined clients recorded no update samples in the measured window gets a **warning** in `warnings` and under its PASS/FAIL cell, because its update percentiles are then 0 for lack of data. The warning doesn't fail the phase.
- **Error rate**: error frames and socket errors received in the measured window divided by the actions sent in it (0 when none were sent). Join failures are excluded, so a large action count can't dilute them.
- **One measured window, per-metric keys**: every metric uses the same measured window `[origin + warm-up, origin + duration)`, but each selects its samples by its own timestamp. RTT and update intervals go by completion (receive) time, sends and send lag by actual send time, errors by arrival time, server disconnects by close time, and unanswered requests by intended send time (the RTT origin).
- **Unanswered requests**: `measurement.unanswered` counts the requests still unanswered at the phase end, those of them older than 5 s (`timedOutAtEnd`) and the responses that took longer than 5 s (`lateResponses`). It does this for the whole phase and for requests sent in the measured window. The RTT distributions leave out unanswered requests, so this is their missing count. Requests sent just before the phase end are normally still pending. An unanswered request is forgotten at the phase end, so a late response never lands in the next phase.
- **Windows**: `measurement.windows` has per-window (`--window-ms`, default 1000) RTT and update distributions and sends. Windows are split at the warm-up boundary rather than flagged when they straddle it. They run from the origin to the end of the warm-up and from there to the phase end, so the last warm-up window and the last window can be shorter (`startMs`/`endMs`). A window is flagged `warmup` only when it lies entirely inside the warm-up.
- **Listen queue** (Linux): each phase's `listenQueue` gives two `ListenOverflows`/`ListenDrops` increases from `/proc/net/netstat`: `phase` (from the transition start to the phase end) and `measured` (from origin + warm-up to the phase end). `listenQueue.readAt` records when each read actually happened. `meta.listenQueue.run` covers the whole run. The counters are host-wide (network-namespace-wide in a container), which the fields record as `scope: "host-or-netns"`. ws-loadtest reads the file on its own host, so they describe the server's listen queue only when the server runs on the same host or in the same network namespace (for example, the load client and GameServer in one container), and nothing else there accepts connections. They are absent on macOS, where the JSON leaves these fields out and the HTML report shows `n/a`; macOS still caps the backlog (`kern.ipc.somaxconn`), it just isn't measured. The server's own startup line reports the effective backlog (`effectiveListenBacklog`, `somaxconn`; #124).
- **Client events** (`events` in the scenario, or `--move-to-rate`): each player also sends client events, each on its own spread schedule (`period = 1000 / ratePerSecond`, a per-connection offset keyed by event name). Events get no response, so they never enter RTT; RTT stays on the actions. `measurement.events` gives, per event, the sends in the measured window, the achieved rate overall and per player, and the target (rate × average joined connections).
- **State-update payload bytes**: the payload size of every state update is recorded: the message as `ws` hands it over, not the TCP bytes. When permessage-deflate is negotiated (the `ws` client offers it), that is the size after inflation, so `connectionLifecycle.permessageDeflate` (per phase) and `meta.permessageDeflate` (over the run) count the connections opened with and without it. `measurement.stateUpdates` gives the updates in the measured window, updates per second (overall and per player), and the payload size in bytes (`bytesMean` and the `bytes` distribution, p99 included). Like the update intervals, a connection's first update (its join snapshot) is left out. The HTML report shows updates per player per second, payload bytes mean / p99 and events per player per second next to RTT.
- **Load client CPU**: every worker samples its own process CPU time (`process.cpuUsage()`, user + system) every 500 ms through the phase. `measurement.clientCpu` gives each worker's share of one core over the measured window (`perWorkerPct` min / mean / max), the orchestrator process sampled the same way (`orchestratorPct`, null if its samples miss the window), workers and orchestrator together (`totalPct`, % of one core) and the cores the client sees. A worker near 100% means its event loop, not the server, may be adding to RTT; the HTML report shows it next to the other phase columns. Server CPU comes from the system metrics (below).
- **Load client event-loop utilization**: every worker also samples its cumulative event-loop active and idle time (`performance.eventLoopUtilization()`) every 500 ms. `measurement.clientElu` gives each worker's ELU over the measured window (`perWorker` min / mean / max, 0–1; null when no worker's samples covered it) and how many workers' samples covered it (`workers`). With `clientCpu` it is the check that the load client isn't the bottleneck it measures; unlike the `loop` spans of `--samples-dir`, it needs no per-event samples.
- **Server CPU**: `monitoring/collect-system-metrics.sh` (a wrapper around `collect-system-metrics.mjs`) samples the server process every second: its cumulative CPU time (`cpuSec`, user + system; `/proc/<pid>/stat` on Linux, `ps -o time=` elsewhere) with a monotonic clock (`monoMs`) and the wall clock (`tsMs`), plus RSS and load. Each sample's `cpuPct` in the report is the rate over the interval since the previous sample (100 = one core; null for the first). The report's `serverCpu` block gives, per phase over its measured window, the time-weighted mean, p95 and max of those rates, from the intervals wholly inside the window. The sampler used `ps -o %cpu` before 2026-11-05: on Linux that is CPU time over the process's whole lifetime, so `cpuPct` in older reports lags the load and includes start-up and the join ramp; those files have no `cpuSec` and give `serverCpu: null`. Re-derive or re-measure before citing their server CPU.
- **Load client event-loop delay**: every worker monitors its own event loop (`perf_hooks.monitorEventLoopDelay`, 1 ms resolution) from the measured window's start to the phase end. `measurement.clientLoopDelay` gives the delay beyond the 1 ms sampling interval: p50 and p99 across workers (`mean`, and `max` for the worst worker) and the longest single delay (`maxMs`), in ms. The HTML column shows the worst worker's p50 / p99 and the longest delay. A high p99 there means late frame reads and send timers on the client, which inflate RTT and send lag.
- **Closest to the old tool**: `--layout per-connection --connect burst --boundary abrupt --send lockstep --warmup-seconds 0`.

## Kernel socket memory (Linux)

`node dist/sockstat-main.js --out <file.jsonl> [--netns a,b,-] [--interval-ms 1000]` samples TCP socket memory and queues every interval until SIGINT or SIGTERM, one JSON line per sample (`src/sockstat.ts`). `--netns` lists `ip netns` names, `-` being the sampler's own namespace; it needs the rights `ip netns exec` needs. It runs `cat` and `ss` in every namespace each interval, so pin it to the load client's CPUs (`taskset -c <client cpus>`), away from the server's.

Only some of `/proc/net/sockstat` is per namespace. In its TCP line, `inuse` and `tw` are the namespace's own, but `mem`, `orphan` and `alloc` are host-wide, whichever namespace reads them (`net/ipv4/proc.c`). So each sample has `hostTcpMemPages` and `hostTcpOrphan` once. On one host they count both the load client's and the server's sockets. What a namespace's sockets hold comes from `ss -tnH exclude listening` in it: the count and the summed and largest `Recv-Q` (received, not yet read by the application) and `Send-Q` (sent, not yet acknowledged), for the established sockets and, apart, for each other state. A server close with data still queued leaves the socket in `FIN-WAIT-1` or `LAST-ACK`, and its Send-Q is the backlog draining.

## Scenario Format

Scenarios are JSON files under `scenarios/<landType>/` (`hero-defense/`, `visibility-test/`). Each contains:
- `serverUrl` and `landType` (optional): the land type sent in every join. Without `landType` it is the last segment of a `/game/<landType>` server path, else `hero-defense`.
- `actions` with weights + payload templates
- `phases` (`preflight`, `steady`, `postflight`) with durations, rooms, players, rates, and thresholds

- `events` (optional): client events every player sends, e.g. `[{ "name": "MoveTo", "ratePerSecond": 2, "payloadGenerator": "moveTo" }]`, and `eventSeed` (optional integer, default 1) for the payload generators.

**Moving players** (`--move-to-rate <n>`, `--event-seed <n>`): players send `MoveTo` client events at `n` per second each, overlaid on any scenario and any CLI overrides. A positive rate sets (or replaces) the scenario's `MoveTo` event; `0` removes it; without the flag the scenario's `events` stand. The `moveTo` generator draws each target uniformly inside the hero-defense world (128 × 72) from a PRNG seeded per connection by the event seed, the event name and the connection, so with the same seed every connection draws the same target sequence: its n-th target is the same in every run. How many targets a connection sends depends on when it joined, so two runs share the same prefix of each sequence, not necessarily the same count. Targets are encoded with the SDK's `Position2`/`IVec2` (fixed point), loaded from `@swiftstatetree/sdk` (a `file:` dependency on `sdk/ts`; `npm install` builds it). `meta.runConfig` records the effective `events`, the `eventSeed` and the client's `nodeVersion`. `scenarios/hero-defense/moving-players.json` is `default.json` with `MoveTo` at 2/s as an example; for capacity runs, add `--move-to-rate 2` to the usual scenario and overrides instead.

**Network impairment runs** (`scenarios/hero-defense/impairment-{300,10}[-bo75].json`, and `impairment-300-srcal.json` with a 180 s pause for the SR calibration, design `Notes/plans/2026-11-07-network-impairment-experiment-design.md`): the whole run, warm-up through tail, is the first phase, which starts at `--start-at`, the origin `--slow-read` and the impairment schedule count from. Its `impairment` block gives the timeline (15 s warm-up, 30 s baseline, 60 s impaired or 75 s for BO75, 90 s recovery, and a 45 s tail that holds the convergence check), and `tests/impairment-scenarios.test.ts` checks the phase covers it. Steady and postflight are 5 s tails in the same rooms, so their connections are reused. SR runs schedule the profile `SR`, which shapes like P0 but names SR in the timeline, so the analysis applies SR's criteria. `serverUrl` is the server's address in the impairment topology, 10.200.0.1, and the thresholds are open: the run's criteria are the analysis's.

**Visibility test land** (`scenarios/visibility-test/`, #65): the land on `/game/visibility-test` moves 40 entities and syncs them through a per-player filter, so it exercises per-player projection at load. Its scenarios use 4 players per room (one per viewer slot), `SetMotionAction { enabled: true }` as the RTT action (it keeps the entities moving), and `MoveViewer` client events at 2/s from the `moveViewer` generator, which draws each viewer position uniformly inside the 100 × 100 arena the same way `moveTo` does. The land has no `StateSync`: it syncs in each 50 ms tick, so the scenarios set `syncIntervalMs: 50` and `updateP95: 70`. In a 1-room smoke run on a Mac, clients saw 20 updates per player per second, with intervals of p50 50 ms and p95 53 ms, and update sizes of p50 99 B and p95 197 B (broadcast and per-player frames together).

**Resolver test land** (`scenarios/resolver-test/`, #65): the land on `/game/resolver-test` answers `CallServiceAction` only after its resolver has called a simulated external service, so a run keeps resolvers pending at load. The service is configured on the server: `RESOLVER_TEST_DELAY_MS` (default 200), `RESOLVER_TEST_DELAY_JITTER_MS` (0), `RESOLVER_TEST_FAILURE_RATE` (0, from a seeded per-land counter), `RESOLVER_TEST_DEADLINE_MS` (1000), `RESOLVER_TEST_SEED` (1) and `RESOLVER_TEST_IGNORE_CANCELLATION` (false; `true` makes every call wait its whole delay when cancelled, so the framework's resolver deadline leaves it running). RTT includes the delay, so the scenarios set `rttP95: 400` and `rttP99: 600` for the default 200 ms.

`RESOLVER_TEST_JOIN_FAILURE_RATE` and `RESOLVER_TEST_LEAVE_FAILURE_RATE` (default 0) make the land's OnJoin and OnLeave checks fail at those rates, seeded per land and kind. A failed join reaches the client as `JOIN_DENIED` with the check's message and counts as a join failure, so such a run passes `--allow-join-failures`; `connectionLifecycle.joinFailures.injected` counts the ones the check failed on purpose (the message is pinned in the same fixture). A failed leave isn't visible to the client: the player is removed without the OnLeave handler, and the land's broadcast `joins` and `leaves` count the handlers that ran.

`RESOLVER_TEST_TICK_PROBE_PATH` makes GameServer time resolver-test's ticks on the server: the gap between consecutive tick handler starts of each land, merged into a 1 ms histogram, appended as one JSONL line per window `(fromTs, ts]` (`RESOLVER_TEST_TICK_PROBE_INTERVAL_MS`, default 1000; `ts` as in the transport profiler's lines, the server's wall clock). `ticks` exceeds `gaps` by the lands whose first tick fell in the window: a land's first tick has no gap. Re-evaluation registers no probe, so records and replays don't change.

The failures such a run injects are not errors. Each phase's `phaseTotals.actionOutcomes` counts every request's first answer once: `applied` (an action response), `failed` (the service threw or passed its own deadline), `timedOut` (the framework's `RESOLVER_TIMEOUT_MS` fired) and `errored` (any other error, also in `errorCount`); `answeredAfterPhaseEnd` counts those of them answering a request an earlier phase end left unanswered, and `unmatched` answers that weren't a request's first (a second answer, or an unknown request). Over a run, actions sent equal applied + failed + timedOut + errored plus the last phase's `pendingAtEnd`. Each join-failure record names the land it tried to join (`land`), for per-land counts of injected join failures. The phase's `rtt` holds every answer's round trip; `phaseTotals.appliedRtt` only the applied ones', and with `--samples-dir` each `rtt` record carries its `outcome`. A `timedOut` answer also comes from a real overload, with the same message, so a run that injects no framework timeout must treat any as a failure. Failed and timed-out answers are told by their `ACTION_HANDLER_ERROR` message (`src/action-outcomes.ts`, #304 asks for structured codes); the strings are pinned in `tests/fixtures/resolver-failure-messages.json`, which a GameContent test checks against the server. Every other error, an `ACTION_HANDLER_ERROR` with any other message included, stays in `errorCount` and fails the phase. The load client's response timeout is 5 s, so a run whose framework deadline is above that sees a slow answer as pending, not timed out.

**Thresholds and sync interval**: For lands that use `StateSync(every: N ms)`, set update thresholds to **N + margin** (e.g. Hero Defense: StateSync 100ms → `updateP95: 120`, `updateP99: 250`). This accounts for client-observed interval including event-loop jitter; do not set `updateP95` to exactly N or healthy runs may fail. You can set **`syncIntervalMs`** in the scenario root (e.g. `100`); if a phase’s `thresholds` omits `updateP95`/`updateP99`, they are derived as `syncIntervalMs + 20` and `250`.

## Metrics

[METRICS.md](METRICS.md) defines every reported metric (start and end events, clock, window, aggregation, confounds) and lists the method changes since February 2026.

- **rtt**: Round-trip time from the action's intended send time (`spread`) or actual send (`lockstep`) to receiving its actionResponse. Measures server + network + client-side queueing.
- **inputToVisible** (`--input-latency on`; off by default): input-to-visible latency, from sending a move event to the first state update whose payload shows it. Both lands echo the event's point into synced state unchanged: Hero Defense `MoveTo { target }` sets the player's `targetPosition` (the `moveTo` generator draws targets inside the world, so the clamp never changes them), visibility-test `MoveViewer { position }` sets the viewer's `position`. The server diffs a `Position2` as one value, so the point arrives whole: a keyed `{ v: { x, y } }` object in JSON, and positionally as `[x, y]` in the opcode encodings since #271 (atomic values sent positionally). The client keeps up to 8 pending points per connection and scans the state part of each state frame (not its events, which carry other positions) for either shape while any is pending, with no schema and no state reconstruction. `measurement.inputToVisible` gives, for the move events sent in the measured window, `sent`, `seen`, `superseded` (dropped from the 8 pending by a newer one), `timedOut` (not seen within 5 s) and the `latencyMs` distribution; events still pending at the phase end are not counted. The key is absent when no move event was tracked, so reports keep their shape. The HTML report shows p50 / p95 / p99 and seen / sent next to RTT. A phase that sent at least 100 tracked inputs fails when fewer than 95 % were seen (`--input-latency-min-seen <share>`, `0` turns the check off; `run-ws-loadtest.sh` forwards it): a wire change that hides the echoed point from the matcher fails the run instead of emptying the metric. Caveats: like `update`, it includes the client's event-loop delay (`Date.now()` when the `message` callback runs); a false match needs another object in the same frame with exactly the same fixed-point x and y. It is off by default because the scan costs load-client CPU: on the Mac (8 cores, 4 workers, `profile-100rooms` with `--move-to-rate 2`, release GameServer), the steady phase's total client CPU was 25.8 % and 27.2 % without it and 29.2 % and 29.5 % with it, so turn it on for latency runs and leave it off when the load client's headroom matters.
- **update** (update inter-arrival): **Client-observed** interval between consecutive state updates (time between handling one sync's state and the next in the same connection). It is not a latency: a server that delivers every update equally late shows the same intervals; `inputToVisible` measures latency. The JSON key stays `update`. One sync is one update, even when it arrives as two frames: with messagepack (opcodeMessagePack state updates) a land with per-player fields sends each session the merged broadcast frame (opcode 107) and then its per-player state frame. jsonObject and opcodeJsonArray send one combined state frame per session and sync, so the grouping never applies to them. A plain state frame within `SYNC_FRAME_GROUP_MS` (10 ms) after a 107 frame, with no state frame between them, is counted as part of that sync, and its bytes are added to the sync's size. Hero Defense has only broadcast fields and sends one 107 frame per sync, so its counts are the same with or without the grouping. The window is a timing heuristic: the frames carry no tick marker, and the server sends a per-player frame without a 107 frame when a sync changes only per-player state, so a plain frame after a 107 frame cannot be assigned structurally. Under heavy client load the two halves of one sync can arrive more than 10 ms apart; they then count as two updates again. `measurement.stateUpdates.syncFrameGrouping` reports, per phase, how many plain frames after a 107 frame were `grouped` and how many were `ungroupedAfterBroadcast`. For visibility-test, whose broadcast `tickCount` changes every tick, the second should stay near 0; if it grows with load, that run's update rate and sizes are distorted. Before 2026-11-06 each frame counted as an update, so visibility-test runs from before then show about twice the update rate and half-size updates. Uses `Date.now()` when the `message` callback runs. Hero Defense uses **StateSync(every: 100ms)** = 10 broadcasts/s.
  - **Worst case**: The server sends on time (e.g. at t=0 and t=100ms). The client receives both packets on time, but the *callback* for the second packet runs a few ms late (event loop busy with other connections). So we record "last update" at t=104 instead of t=100 — i.e. we observe 104ms between updates even though the packet arrived in time. So the measured interval = server interval + client processing delay.
  - **Thresholds**: When setting `updateP95` / `updateP99`, use **server sync interval + margin for client jitter** (e.g. 100ms + 20ms = 120ms for Hero Defense). Do not set the threshold to exactly the server interval (100ms), or healthy runs will fail due to client-side jitter.

- **Can we prove the client has no delay?** There is **no direct metric** for client processing delay: Node.js `ws` does not expose packet arrival time, so we only record `Date.now()` when the `message` callback runs. You can use **indirect evidence**:
  - **RTT p95 low** (e.g. &lt; 10ms): action requests and responses are handled quickly → the client event loop is not globally backlogged.
  - **update p50 ≈ server sync interval** (e.g. ~100ms): the median interval between state updates matches the server’s StateSync interval → the server is sending on time.
  - When both hold, **update p95 above the sync interval** (e.g. 104ms vs 100ms) is consistent with occasional client-side jitter, not systematic client delay (which would also raise RTT). The HTML report can show a short note when these conditions are met.

## Log level during load test

**When using the script** (`run-ws-loadtest.sh` or `run-scalability-test.sh`): the script starts GameServer with **`LOG_LEVEL=error`** and redirects all server output to `/tmp/ws-loadtest-gameserver.log`. Only script messages and the final "Report written to ..." appear in the terminal; server logs are not printed. If a run fails or the server crashes, the script prints the tail of that log.

**When you start GameServer manually** (e.g. in another terminal for debugging): set **`LOG_LEVEL=error`** so only errors are shown during the load test. Otherwise the default `info` level will print many lines per connection (e.g. "Client connected", "Client joined", "Received action", "Sending state update"):

```bash
# In the terminal where you run GameServer (performance test: only errors)
LOG_LEVEL=error swift run GameServer
```

Optional: `NO_COLOR=1` for plain text logs (e.g. when redirecting to a file).

## Transport profiling (server-side)

When `--profile` is used with `run-ws-loadtest.sh` or `run-scalability-test.sh`, the GameServer writes **JSONL** to `<output-dir>/transport-profile.jsonl` every second. Each line contains:

- **counters**: actions, stateUpdates, messagesReceived, bytesReceived, disconnects, errors, connectedSessions, joinedSessions
- **lag_ms**: actor ticker drift (expected 1000ms interval vs actual)
- **decode_ms**, **handle_ms**, **encode_ms**, **send_ms**: latency percentiles (p50/p95/p99/max) when samples exist (1% sampling to minimize overhead)

Environment variables (optional): `TRANSPORT_PROFILE_JSONL_PATH`, `TRANSPORT_PROFILE_INTERVAL_MS` (default 1000), `TRANSPORT_PROFILE_SAMPLE_RATE` (default 0.01), `TRANSPORT_PROFILE_MAX_SAMPLES_PER_INTERVAL` (default 500).

## Reconstruction-equals-projection gate (`verify-views`)

`EncodingBenchmark --capture-views <dir>` (hero-defense multi-room runs, and visibility-test runs through the generic runner, whose `--record-dir` also writes each captured room's re-evaluation record for `ReevaluationRunner --verify`) writes, for the first
`--capture-rooms` rooms (default 10), every frame each room sends with its target, and after
every sync each player's projection, as `<dir>/<run>/room-<i>.ndjson`. `verify-views` rebuilds
every recipient's state from the frames addressed to it with the TypeScript SDK, as a client
does, and compares it with that player's projection after every sync (the convergence check's
`compareStates`):

```bash
npm run build
node dist/verify-views-main.js --capture <dir> --out report.json
```

It exits 1 when any recipient differs after any sync, any frame fails to decode, or the
capture is empty; the report lists the first differing paths per sync and recipient.
`deep-research/snapshot-baseline/run.sh` runs it after every cell.

A capture from the entity-delta baseline (`EncodingBenchmark --baseline entity-delta --parallel
false`, plan `Notes/plans/2026-11-07-entity-delta-baseline.md`) has `format: "entity-delta"` in
its header; its frames are the baseline's, not SST's, and `verify-views` decodes them with
`src/entity-delta.ts`, a TypeScript implementation separate from the Swift encoder, against the
same projections. `--no-server-events` turns the land's server events off for a run (both SST's
frames and the baseline's then carry state only); the projections are the same with it on and off.

## The `@colyseus/schema` baseline (`colyseus-baseline`)

`colyseus-baseline` converts an `EncodingBenchmark --capture-views` directory into a capture of
`@colyseus/schema` frames (version pinned in `package.json`), from the captured projections:
hero-defense's broadcast state declared as Colyseus schema classes (`src/colyseus-baseline.ts`),
one encoder per room, `encodeAll()` for the first checkpoint and `encode()` plus
`discardChanges()` after assigning the changed values for each later one, each frame to every
session. `--typing number` declares every number `number`; `--typing tuned` declares each field
the narrowest fixed type covering the values it took in the run. The header carries
`format: "colyseus-schema"`, the package version and the field types, so `verify-views`
(Colyseus's `Decoder`, the decoded state mapped back to the projection's shape) and `time-decode`
(`Decoder.decode` alone) read it like any other capture.

```bash
node dist/colyseus-baseline-main.js --capture <dir> --out <b1-dir> --report b1.json [--typing number|tuned]
node dist/verify-views-main.js --capture <b1-dir> --out b1.views.json
```

## Client decode cost (`time-decode`)

`time-decode` times the TypeScript SDK decoding recorded frames as a client does: every
recipient's stream in order, with that stream's own dynamic-key tables. It reports two figures
per stream: `decode` (`decodeMessage` alone) and `decodeApply` (decode plus applying to a
`StateTreeView`, the client's cost per frame). Each pass starts from fresh key tables and a fresh
view; the figure is the median pass after the warm-up passes, per frame and per sync (a sync is
one checkpoint of the capture: every frame a recipient got for that sync). It also reports the
frame-size distribution.

```bash
npm run build
taskset -c 0-7 node dist/time-decode-main.js --capture <dir> --out time-decode.json [--passes 20] [--warmup 3]
node dist/time-decode-main.js --recording tests/fixtures/hero-defense-frames-messagepack.json.gz --out <file>
```

The input is an `EncodingBenchmark --capture-views` directory (every run in it), or a GameServer
recording from `scripts/record-frames.mjs`, timed from after each join response with the
encoding it switches to. A frame the SDK can't decode fails the run.

A capture from the entity-delta baseline (`format: "entity-delta"`) is timed with
`src/entity-delta.ts` instead of the SDK. That decoder applies as it parses, so such a run has
`decodeApply` only, and `decode` is null.

For a capture, each run also gets `roomBytes`: the payload bytes to every recipient of a room per
measured sync (checkpoints after the first), mean over the captured rooms, before and after
permessage-deflate (`bytesPerRoomSync`, `deflateBytesPerRoomSync`). The deflate figure compresses
each recipient's whole stream in order with one raw-deflate context (context takeover, 15-bit
window, level 6, as `ws` runs it by default), a sync flush per message with its trailing
`00 00 ff ff` removed (RFC 7692). Checkpoint 0 is compressed, since it sets up the context as on
a real connection, but isn't counted.

Provenance: the output records node's and V8's versions, the CPUs the process may run on (Linux),
and the commit the SDK and this tool were built from. Each capture's header records the
benchmark's commit, whether its tree was dirty, the cell's parameters and the sync settings from
the environment. For a capture, the SDK's commit must equal every run's benchmark commit and both
trees must be clean, or the run exits 1 after writing its report.
`--allow-unverified-provenance` writes the report with `provenance.verified: false` and the
problems listed instead, for a trial run off the measurement machine; its numbers aren't for
tables.
